本仕様は [[WACZ]] のプロファイルです。WACZ パッケージの書き方を制約し、BrowserHive が その中に記録する追加の member を定めます。アーカイブだけを手にした読み手が、その取り込みが 何を取得し何を取得できなかったか、どのような設定の下で走ったかを判断できるようにするためです。

これは作業中の草案です。BrowserHive が現在書き出しているものを記述しています。同プロジェクト 以外での位置づけを持たず、[[WACZ]] の発行者から承認されたものでもありません。

この版は、取り込んだページのスクリプトが乱数として受け取った値をパッケージが持つかどうかを、 browserhive:capture の random として述べることをすべてのパッケージに求め （ を参照）、その値と、それを記録したコードを持つエントリ random/values.jsonl と random/recorder.js を定めます （ を参照）。random を持たない 1.25.0 向けのパッケージは、 1.26.0 に適合しません。これは 意図されたもので、conformsTo が版を名指ししているのはそのためです —— 古い パッケージを持つ読み手も、それが何に対して書かれたかを辿れます。 以前の版 —— 1.0.0・1.1.0・1.2.0・1.3.0・1.4.0・1.5.0・1.6.0・1.7.0・1.8.0・1.9.0・1.10.0・1.11.0・1.12.0・1.13.0・1.14.0・1.15.0・1.16.0・1.17.0・1.18.0・1.19.0・1.20.0・1.21.0・1.22.0・1.23.0・1.24.0・1.25.0 —— がそれぞれの URL で公開され続けるのはこの理由によりますが、 BrowserHive はもうそれらを出力しません。

取り込みは、ページをいつ撮ってよいかを決めなければならず、どの決め方も賭けです —— 固定の間は、もう揃っていたページから時間を奪い、揃っていないページには足りません。 合図で終える待ちは、合図より先に期限に当たることがあります。1.7.0 より前は、パッケージは そのどれが起きたかを言えませんでした。これはパッケージを証拠として読む人にとって 重要です。「ページはこう見えていた」と「ページはまだ読み込み中に、こう見えていた」の 違いは、パッケージの他のどこからも取り戻せません —— 記録が言うのは届いたものであって、 取り込みが先へ進んだときにまだ向かっていたものではないからです。

Introduction

[[WACZ]] のパッケージは、何が取り込まれたかを述べます。しかし何が抜けたかは述べず、 どのような条件下で取り込みが走ったかも述べません。それらは取り込み時にしか知り得ず、 取り込みを行ったプロセスが終了した時点で失われます。

この喪失が問題になるのは、旅をするのがアーカイブの方だからです。3 年後にパッケージを開いた 読み手には、API の応答も、それを作った機械も、その機械が持っていたログも残っていません。 「ここに欠けているものはあるか」にパッケージ自身が答えられないなら、他の誰も答えられません。

そこで本プロファイルは、パッケージが取り込みについての自身の申告を運ぶことを要求します —— どの本文が欠けていてそれはなぜか、どの上限が効いていたか、どのリクエストを送らず どのリクエストを送って保持しなかったか、記録の前にページから何を取り除いたか、 どのシークレットを渡され、そのどれを残したか、 各オリジンがどの証明書を提示したか、取り込みが走りながら書いたログ、取り込みが 始まりを見た要求と、そのそれぞれがどう終わったか、取り込んだページの画像を残したか どうかと、残さなかったときはその理由、そして、記録を求められたときは、取り込んだページの スクリプトが乱数として受け取った値。これらは [[WACZ]] の意味を何ひとつ変えません。変えずに、そのままでは取り戻せないものを記録します。

Conformance

本仕様の適合対象はパッケージ、すなわちファイル 1 つです。適合はファイルの性質で あって、それを書くソフトウェアの性質ではありません。ある実装が、あるときは適合する パッケージを、別のときは適合しないパッケージを書くことはあり得ます。本仕様はそのどちらで あるかについて何も述べません。

適合するパッケージは、適合する [[WACZ]] パッケージです。本仕様は要求を追加します。 取り除くことも、緩めることもしません。

本仕様のいずれかの版に適合するパッケージを BrowserHive WACZ と呼びます。 BrowserHive WACZ はどれも WACZ パッケージです。それ以外の WACZ パッケージが何を持つかに ついて、本仕様は何も求めません。

本仕様における MUST（〜しなければならない）、 MUST NOT（〜してはならない）、 SHOULD（〜すべきである）、 MAY（〜してもよい）は [[RFC2119]] の記述に従って解釈されます。

JSON の member 名は大文字と小文字を区別します。timestamp を保持すると記した member の値は、 UTC の [[RFC3339]] date-time でなければならない。

The browserhive:capture member

適合するパッケージの datapackage.json は、値が JSON オブジェクトである browserhive:capture という名前の member を持た なければならない。

この member を config または metadata の中に置いては ならない。これらの名前は [[WACZ]] の読み手にとって意味を持ちます （ を参照）。

ここで定義されていない member が browserhive:capture に存在しても よい。読み手は認識しない member を無視し なければならない。

Conformance declaration

browserhive:capture は、そのパッケージが満たすと主張する本仕様の版の URL を 値とする conformsTo という member を持たなければならない。 

"browserhive:capture": {
  "conformsTo": "https://uraitakahito.github.io/browserhive-specs/wacz-profile/1.26.0/"
}

宣言をここに置き、datapackage.json の profile member に置かないのは、 そちらがこの用途に使えないためです。

読み手は browserhive:capture が存在するというだけで、また、パッケージやその中の ファイルの名前から（ と を参照）、 適合を推定しては ならない。conformsTo が無ければ、そのパッケージが どの版に向けて書かれたかは不明です。

build

browserhive:capture は、パッケージを作ったソフトウェアを機械可読な形で 識別する build member を持たなければならない。

Member型必須意味
versionstringはいリリースの識別子。
revisionstringはいビルド元のソース revision。
buildTimestringはいソフトウェアがビルドされた時刻。
 
"build": {
  "version": "3.4.0",
  "revision": "0776cae",
  "buildTime": "2026-08-21T04:04:09.000Z"
}

version の書式は定めません。リリースそのものから作られた build は "3.4.0" のような値を持ちますが、リリースとリリースの間で作られた build は "3.4.0-12-gabc1234" のように、直近のリリースからの距離を含んだ値になり 得ます。どちらも「どの build か」を言うという点では同じで、読み手はこれを版数として 解釈するのではなく、同じ値なら同じ build であるという識別子として 扱うべきです。

[[WACZ]] は既に software を定めています。あちらは散文で、書き方が producer ごとに違うため誰も解析しません。build があるのは、同じ事実を形式を推測せずに 機械が読めるようにするためです。

browser

browserhive:capture は、取り込みを行った browser を記述する browser member を持たなければならない。値が string である product member を持たなければならない。 

"browser": {
  "product": "Chrome/151.0.7922.137"
}

綴りは定めません。値は browser 自身が名乗るものなので、別のエンジンが作った パッケージは別の形を運びます。読み手は 2 つの値が等しいかどうかを比べられますが、 書式を仮定することはできません。

値は代用のものであってはならない。これを取得できない producer は、 適合するパッケージを作ってはならない。記録した browser が不明な アーカイブはこのプロファイルの外にあり、member を省くことはそれを表明する手段では ありません。

settings

browserhive:capture は、この取り込みに効いていた設定を記録する settings member を持たなければならない。

値は解決後の値でなければならない。要求が指定した値ではありません。 何も指定しない要求も何らかの設定の下で走っており、アーカイブが報告すべきなのはその設定です。

Member型必須意味
signaturestringはい "required" または "none"。この取り込みが署名なしで 出されてよかったか。
viewportobjectはい member width と height。ともに整数、単位は CSS ピクセル。
devicePixelRatiosarray of numberはい ページを読み込んだときの device pixel ratio を、読み込んだ順に。要素数が そのまま読み込みの回数。
sessionstringはい その取り込みのために作られ、終われば捨てられる browser context で 走ったのか、取り込みをまたいで使い回される context で走ったのか。 前の取り込みが残した状態にパッケージが依存しうるかどうかを、 読み手はこれで判定します。
userAgentstringはい 取り込みが送った User-Agent。要求が指定した値を解決した後の値で、 指定が無ければブラウザ自身の値。
behaviorsarray of objectはい 読み込み後に走った behavior。走った順のまま。 各項目は id（その behavior が走った名前）と origin（"builtin"・"site"・ "custom" のいずれか）を持ちます。自前の behavior を 持たない producer は、すべての項目に "custom" と書きます。 behaviors ディレクトリを参照。
preloadarray of objectはい 遷移の前に走らせるために持ち込まれたスクリプト。登録した順のまま —— 報告したものではありません（それら自身は何も報告できないため）。 各項目は id（持ち込まれた名前）を持ちます。空の配列は 「1 本も持ち込まれなかった」と述べます。 preload ディレクトリを参照。
variablesobjectはい behavior が読むために要求が渡した値を、名前ごとに。値はどれも文字列。 空のオブジェクトは「1 つも渡されなかった」と述べます。 を参照。
secretsarray of stringはい behavior が読むために要求が秘密として渡した値の名前を、名前順に。 名前だけ —— この member は値を持ちません（下を参照）。空の配列は 「1 つも渡されなかった」と述べます。
secretArchiveobjectはい それらのシークレットのうち、要求が WARC のレコードに残すことを求めたもの。 各 member の名前は secrets の項目で、値は文字列 "keep"。ここに名前の無いシークレットは隠します。 空のオブジェクトは「1 つも残さなかった」と述べます。 を参照。
limitsobjectはい この取り込みに効いていた上限。member maxResponseBytes と maxTaskBytes（本文の上限）、maxWarcBytes（新しい WARC ファイルを 始める大きさ。 を参照）。3 つとも整数で、単位はバイト。
urlPoliciesarray of objectはい 効いていた URL パターンのそれぞれに対して取り込みが何をしたかを、 評価した順に。urlPolicies を参照。
contentTypePoliciesarray of objectはい 効いていたメディア型のそれぞれに対して取り込みが何をしたか。 contentTypePolicies を参照。
acceptLanguagestringいいえ 取り込みが設定したときにのみ存在する。オリジンが返すものが変わるため。
 
"settings": {
  "signature": "none",
  "viewport": { "width": 1280, "height": 800 },
  "devicePixelRatios": [1],
  "session": "isolated",
  "userAgent": "Mozilla/5.0 (X11; Linux x86_64) AppleWebKit/537.36 (KHTML, like Gecko) HeadlessChrome/151.0.0.0 Safari/537.36",
  "behaviors": [
    { "id": "autoscroll", "origin": "builtin" },
    { "id": "autofetch", "origin": "builtin" }
  ],
  "preload": [],
  "variables": {},
  "secrets": [],
  "secretArchive": {},
  "limits": {
    "maxResponseBytes": 20971520,
    "maxTaskBytes": 209715200,
    "maxWarcBytes": 1000000000
  },
  "urlPolicies": [
    { "pattern": "*://*.example-analytics.com/*", "action": "deny" }
  ],
  "contentTypePolicies": []
}

この例の session は、取り込みがそれ自身の context で走ったことを 表しています。devicePixelRatios の要素が 1 つなのは、ページを 1 回だけ読み込んだという意味です。behaviors に並ぶ 2 つは実際に走った behavior です —— 有効化されていた ものの一覧ではありません。userAgent がブラウザ自身の値なのは、要求が指定 しなかったからです。acceptLanguage は、この取り込みが設定しなかった ので在りません。variables・secrets・secretArchive が 空なのは、要求が behavior に値を 1 つも渡さなかったからです。値そのものは producer が決めるもので、ここに挙げた綴りを このプロファイルが定めているわけではありません。

例外は origin です。behavior の id はそれを提供した側が 決めた名前で、本仕様はその綴りについて何も述べません。しかし origin が答えるのは behavior についての問いではなく パッケージについての問い —— そのコードは producer から来たのか、 リクエストから来たのか —— なので、この 3 値はここで定めます。

devicePixelRatios が数値ではなくリストなのは、取り込みがページを 2 回以上 読み込むことがあるためです。単一の値で記録すると、在る描画が無いと読み手に 伝えてしまいます。

値は読み込んだ順序で並んでいなければならない。読み手が 「どの版がアーカイブに在るか」だけでなく「どの版が最後に描かれたか」を言えるように するためです —— ページの見た目を伴う成果物は、最後の読み込みが残した状態に従います。

2 回読み込む取り込みでは、読み込んだ数だけ値が並びます。要求が User-Agent を 指定した場合は送った値が現れ、acceptLanguage を指定した場合は、それもここに 現れます。behavior に値を渡した 要求では、その値も現れます —— 変数は値ごと、シークレットは名前だけで、 残すことを求めたものは secretArchive に: 

"settings": {
  "signature": "required",
  "viewport": { "width": 1280, "height": 800 },
  "devicePixelRatios": [1, 2],
  "session": "isolated",
  "userAgent": "Mozilla/5.0 (X11; Linux x86_64) AppleWebKit/537.36 (KHTML, like Gecko) Chrome/151.0.0.0 Safari/537.36 BrowserHive",
  "behaviors": [
    { "id": "autoscroll", "origin": "builtin" },
    { "id": "example.com:gallery", "origin": "custom" }
  ],
  "preload": [],
  "variables": { "query": "gallery" },
  "secrets": ["api_token", "member_id"],
  "secretArchive": { "member_id": "keep" },
  "acceptLanguage": "ja,en;q=0.9",
  "limits": {
    "maxResponseBytes": 20971520,
    "maxTaskBytes": 209715200,
    "maxWarcBytes": 1000000000
  },
  "urlPolicies": [],
  "contentTypePolicies": [{ "prefix": "video/", "action": "no-body" }]
}

2 つは測る対象が違います。maxResponseBytes は レスポンス 1 件の本文に掛かり、maxTaskBytes はこのパッケージへ書いた 本文の累計に掛かります。写しとスクリーンショットも、同じ線に照らします: 残すと、 取り込みが残すバイト数がその線を超えるものは、残しません（snapshots と screenshots を参照）。

この違いは読み手にとって実際的です。maxResponseBytes は 1 件ずつを量るので、 それを下回るレスポンスは何件でも入り、パッケージ全体の大きさはこの値からは 分かりません。maxTaskBytes は積み上げた総量を見るので、線を越えた 後は大きさに関わらず本文が落ちます —— 落ちた中に小さなレスポンスが 混じっていても、それは矛盾ではありません。

maxWarcBytes は本文の上限ではありません。これで落ちる本文は無く、producer が いまの WARC ファイルを閉じて次を始める大きさです（ を参照）。 ここに記録するのは、読み手が archive/ のファイルを、それを生んだ線と並べて 確かめられるようにするためです。

本文が 1 つも落とされなかった場合でも limits は存在し なければならない。切り詰めがどの線を超えたのかを アーカイブが言える場所は、ここだけです —— body not kept のレコードは落とした事実と 実際の大きさを運びますが、その大きさが多すぎたかどうかは線と並べて初めて分かります。

completeness の truncatedUrls は、この 2 つのどちらを超えて落ちたのかを 区別しません。 対処が違う (前者は 1 件が大きすぎ、後者はページ全体が重い) にもかかわらずです。 区別が要る読み手は、パッケージの外 —— 取り込みが出した報告 —— を見ることになります。

userAgent は送った値で、要求が書いた文字列ではありません。要求は値の一部を producer に埋めさせることができ、オリジンが見たのは埋めた後の値だからです。 WARC-Target-URI が mainPageURL である request レコードは どれも、この値を User-Agent ヘッダに持たなければならない（MUST）。

決まりが掛かるのはそのレコードだけです。ページ自身のスクリプトが出す要求は別の値を持ちうるし、 service worker の要求はパッケージに入らないことがあります。この値が何であれ、browser は 取り込みを行ったブラウザを名指し続けるので、読み手はオリジンに何と伝えたかと、実際に何が 取り込んだかを区別できます。

variables と secrets は、要求が behavior に読ませるために渡したものを 記録します（ を参照）。secretArchive は、 シークレットのどれを残すことを求めたかを記録します。要求が何も渡さなかったときも、 3 つとも存在しなければならない（MUST）。空のオブジェクトと空の配列が、 書き漏らしではなく主張になるようにするためです。

variables は値を運びます。語を検索する behavior は何らかの語の下で走っており、 パッケージを証拠として読む人は、それがどの語だったかを言えなければなりません。 コードだけではそれが言えません —— 同じコードが、どの値の下でも走るからです。

secrets は名前だけを運びます。名前を記録するのは、behavior がこの member の 持たない何かを読んだことを、読み手が分かるようにするためです。 producer は、シークレットの値を secrets と secretArchive に 書いてはならない（MUST NOT）。パッケージの残りが値について何を持つかは が、behavior がその値をどうするかは が述べます。

要求が何も言わないシークレットは隠します。だから secretArchive は、要求が 残すことを求めたものだけを挙げます。secretArchive の名前はどれも secrets の項目でなければならず（MUST）、値はどれも文字列 "keep" でなければならない（MUST）。

behavior の id と同じく、variables・secrets・ secretArchive の名前は値を渡した側が決めたもので、本仕様はその綴りについて何も述べません。secrets の 並びだけはここで定めます —— 名前順です。同じ名前を読んだ 2 つのパッケージが、同じ並びで それを挙げるようにするためです。

completeness

browserhive:capture は、そのパッケージが保持していないもの —— 欠けている本文と、 落ちた target —— についての自身の申告である completeness member を持たなければならない。

Member型必須意味
bodylessUrlsarray of stringはい 304 としてしか現れなかった URL。本文が wire を渡っていないので、 アーカイブは保持し得ません。
truncatedUrlsarray of stringはい サイズ上限に達して取り込みが本文を落とした URL。
uninterceptedUrlsarray of stringはい 本文は wire を渡ったが、producer がバイト列として得られなかったので、 アーカイブが本文を持たない URL（[[BROWSERHIVE-WARC-PROFILE]] の Response payloads を参照）。
crashedTargetsarray of objectはい 取り込みの間に renderer が落ちた、主文書以外の target （ を参照）。
completebooleanはい 4 つの配列がすべて空のとき、かつそのときに限り true。
 
"completeness": {
  "bodylessUrls": [],
  "truncatedUrls": [],
  "uninterceptedUrls": [],
  "crashedTargets": [],
  "complete": true
}

何も欠けなかった取り込みはこの形になります。complete は 4 つの配列から 導かれるので、空の配列 4 つと false という組み合わせは現れません。

次は、3 つの理由すべてで本文を欠いた取り込みです: 

"completeness": {
  "bodylessUrls": [
    "https://example.com/assets/app.css"
  ],
  "truncatedUrls": [
    "https://example.com/media/hero.mp4",
    "https://example.com/media/poster.png"
  ],
  "uninterceptedUrls": [
    "https://example.com/api/feed"
  ],
  "crashedTargets": [],
  "complete": false
}

この取り込みでは、CSS が 304 としてしか現れませんでした —— 本文が wire を 渡っていないので、アーカイブは持ちようがありません。動画とポスター画像は上限に当たって 落ちたものです。feed の本文は届きましたが、producer がバイト列として読めませんでした。 同じ URL が 2 回落ちても、配列には 1 度だけ現れます。

同じページの 2 つの取り込みを比較できるよう、URL の 3 つの配列はコードポイント順に整列されて いなければならない。

3 つが別の member なのは、求められる対応が違うからです。304 はオリジン側の 事情でここからは回復できません。上限で落とした本文はこちら側の事情で、上限を上げれば 戻ります。取り込めなかった本文は producer の失敗で、リクエストの設定をどう変えても戻りません。

正当に本文を持たないレスポンスを列挙してはならない —— redirect、204、要求者が設定した方針で省かれた本文 (urlPolicies の no-body、または contentTypePolicies の項目)、および 隠すシークレットの値を持つので落とした本文。最後のものは、要求者がそのシークレットを 残さなかったことで選んだ結果です（ を参照）。 これらを報告しても、読み手が既に決めたこと以上を何も伝えません。

これは省いた本文の大きさに関係なく成り立ちます。方針で省いた本文は 取り込みがそもそも取りに行かなかったもので、上限で落とされたはずがありません。 maxResponseBytes より大きくても、累計が maxTaskBytes に達した後に 届いても、truncatedUrls に載せてはならない（MUST NOT）。 そこに載せれば、要求者が保存しないよう頼んだ本文を、上限を上げれば取り戻せると 読み手に伝えることになります。

WARC は、同じ本文をレコード 1 つずつで述べます。サーバが送った本文を持たずに記録した 応答には、それぞれ body not kept のレコード （[[BROWSERHIVE-WARC-PROFILE]]）が付き、その truncated が理由を言います。 サイズ上限で落とした本文 —— too-large と task-cap —— の URL は truncatedUrls に、バイト列として得られなかった本文 —— not-intercepted —— の URL は uninterceptedUrls に載ります。 方針で省いた本文 —— url-policy と content-type —— と、 隠すシークレットのために落とした本文 —— secret —— は、どちらにも載りません。

[[BROWSERHIVE-WARC-PROFILE]] は、これらの値を producer の上限と方針で定め、その名前は 言いません。パッケージの中では、それは settings に記録したものです:

truncatedsettings の中の上限・方針
too-large 本文が limits.maxResponseBytes より大きかった。
task-cap 本文を書けば、パッケージに書いた本文の累計が limits.maxTaskBytes を超えるところだった。
url-policy URL に最初に当たった urlPolicies の項目の action が no-body。
content-type contentTypePolicies の項目が media type に当たった。
not-intercepted 設定は無い。本文は wire を渡ったが、producer がバイト列として 得られなかった。
secret 上限でも方針でもない。本文が文字の本文でなく、隠すシークレットの値を持っていた。 隠すシークレットは、secrets の名前のうち secretArchive に 無いものと、それとして扱う値です（ を参照）。

crashedTargets

ページは複数の renderer プロセスにまたがって動くことがあります。別サイトの iframe は自分の プロセスを持ちます。その renderer が落ちても、ページの残りは動き続け、取り込みは終えられますが、 その target が見せていたものは失われます。スクリーンショットのその場所には Chromium が描く灰色の枠が 写りますが、それは画像の中の絵で、アーカイブを読む道具には読めません。保存した文書には、ふだんの iframe の 要素が残るだけです。だからパッケージが自分で言います。

crashedTargets は、取り込みが始まってからパッケージを組み立てるまでの間に renderer が 落ちた、主文書以外の target ごとに 1 つの項目を持たなければならない。

Member型必須意味
typestringはい target の種類。ブラウザ自身の語のまま（iframe・ service_worker など）。
urlstringいいえ target の URL。無い場合は下を参照。
statusstringはい renderer の終わり方。ブラウザ自身の語のまま（プロセスの外から止められたなら killed、プロセス自身が落ちたなら crashed など）。
 
"completeness": {
  "bodylessUrls": [],
  "truncatedUrls": [],
  "uninterceptedUrls": [],
  "crashedTargets": [
    {
      "type": "iframe",
      "url": "https://ads.example.net/slot/1",
      "status": "killed"
    }
  ],
  "complete": false
}

url は、それに最初に当たる urlPolicies の項目の action が no-archive か deny のとき、および document が withheld を持つとき、省かなければならない。target の URL は ページから来るので、要求者が残さないよう頼んだものを運び出してはならない。

配列は url、type、status の順に、それぞれコードポイント順で整列されて いなければならない。url の無い項目は、在る項目より前に置きます。

主文書はここに現れません。パッケージを組み立てる前に主文書の renderer が落ちれば、取り込みは失敗し、 パッケージは書かれません。組み立てを始めた後は renderer が要らないので、落ちてもパッケージの申告は 変わりません。同じサイトの iframe と dedicated worker は主文書の renderer の中で動くので、 それらが落ちることは主文書が落ちることです。

coverage

browserhive:capture は、取り込みがページのどこまで下れたかを記述する coverage member を持ってもよい。

Member型必須意味
scrollExhaustedbooleanはい スクロールがページの終端ではなく段数の上限で止まったとき true —— つまりその下にあるものが一度も要求されていないとき。
scrollStepsnumberはい実際に進んだ段数。
scrolledPxnumberはい 到達した深さの概算。段数 × viewport の高さ。
 
"coverage": {
  "scrollExhausted": true,
  "scrollSteps": 40,
  "scrolledPx": 32000
}

3 つの値は互いを読み合うためのものです。scrolledPx は scrollSteps に settings が記録した viewport の高さを 掛けたもの —— ここでは 40 × 800 —— なので、読み手は一方を他方で検算できます。 そして scrollExhausted が true である以上、 この 32,000 ピクセルは取り込みが止まった地点であって、ページが 終わった地点ではありません。その下にあったものは一度も要求されておらず、 したがってパッケージの他のどこにも痕跡を残していません。

スクロールの behavior が何も報告しなかった場合、coverage は存在しては ならない。既定値を入れて書いてはならない —— scrollExhausted: false はページを覆えたという主張であり、一度もスクロール しなかった取り込みはその主張を得ていません。

settle

browserhive:capture は、読み込み後の待ちがどう終わったか —— ページが静まって終わったのか、まだ動いているうちに期限で終わったのか —— を述べる settle member を持たなければならない。

Member型必須意味
strategystringはい どの合図を、どの順で見たか。この版が定めるのは "fully-loaded" —— load、次に limits.minMs の間を置き、それから network・cpu・dom を並べて見る。
endedBystringはい 見ていた合図がすべて期限の前に満ちたとき "quiet"、そうでなければ "deadline"。
waitedMsnumberはい navigation が返ってから待ちが終わるまでのミリ秒。
devicePixelRationumberはい この観測がどの読み込みのものか。devicePixelRatios の要素の 1 つで、 複数あるときは最後のもの。
limitsobjectはい 効いていた上限。どれも数値で、minMs、maxMs（期限）、 quietMs（静止の合図がそれぞれ満たすべき窓）、 networkConcurrency（静かとみなしてよい要求の数）。
loadobjectはい atMs: document が読み込み終わったのを見た時刻。
networkobjectはい quietAtMs: in-flight の要求が limits.networkConcurrency 以下のまま limits.quietMs 続いた時刻。
cpuobjectはい quietAtMs: long task —— メインスレッドを 50 ms 以上握ったタスク —— が limits.quietMs の間走らなかった時刻。
domobjectはい quietAtMs: 要素の出入りも文字の書き換えも limits.quietMs の間無かった時刻。属性の変化は数えない。
 
"settle": {
  "strategy": "fully-loaded",
  "endedBy": "quiet",
  "waitedMs": 2310,
  "devicePixelRatio": 1,
  "limits": { "minMs": 1000, "maxMs": 3000, "quietMs": 1000, "networkConcurrency": 0 },
  "load": { "atMs": 210 },
  "network": { "quietAtMs": 2205 },
  "cpu": { "quietAtMs": 2104 },
  "dom": { "quietAtMs": 2004 }
}

時刻はすべて navigation が返ってからのミリ秒で、waitedMs と同じ時計で測る。 producer が自分の操作の間に差し込んだ間は、この時計に含まない。

合図の時刻は、合図が満ちたときは数値、先に期限が来たときは null である。 時刻は null であっても書かなければならない。 書かずに省くと「この合図は見ていなかった」と読まれ、それは別の事実です。

endedBy は 4 つの時刻から導かれる。producer は、どれかが null で あるのに "quiet" を書いてはならず、どれも null でないのに "deadline" を書いてもならない。

期限が先に来たページ: 

"settle": {
  "strategy": "fully-loaded",
  "endedBy": "deadline",
  "waitedMs": 3116,
  "devicePixelRatio": 1,
  "limits": { "minMs": 1000, "maxMs": 3000, "quietMs": 1000, "networkConcurrency": 0 },
  "load": { "atMs": 188 },
  "network": { "quietAtMs": 2011 },
  "cpu": { "quietAtMs": 2108 },
  "dom": { "quietAtMs": null }
}

ここではページが文字を書き換え続けていた —— たとえば時計 —— ので、DOM は 1 秒と 静かにならず、取り込みは 3 秒の期限で先へ進みました。通信と CPU は静まっており、 静まらなかったのは DOM だけです。

endedBy: "deadline" は取り込みの失敗を意味しません。パッケージは、その時点までに ページがなったものを保持しています。記録しているのはページが静まっていなかったことで、 それはパッケージを証拠として読む人が知る必要があり、しかもパッケージの他のどこからも 取り戻せないものです。

静止の合図はそれぞれ「limits.quietMs の間ページが動かなかったか」を問うもので、 「この先も動かないか」を問うものではありません。窓より長く黙ってから変わるページは、 変わる前に静まったと読まれます。

dismissal

browserhive:capture は、取り込みが記録の前にページから何を取り除いたか、 そして何を探したかを記録する dismissal member を持ってもよい。

同意バナーを取り除いた取り込みは、そのあと保存する文書そのものを変えています。 それを述べるものは他にありません —— 取り除かれた要素は WARC にも索引にも 描画後のスナップショットにも痕跡を残さず、読み手はもともとバナーの無いページと 区別できません。

Member型必須意味
selectorsobject の配列はい 効いていた選択子。評価した順のまま。 member は framework と selector で、どちらも文字列。
heuristicobjectはい どの選択子も名指ししていない要素の除去を支配していた閾値。 member は enabled (boolean)・ minViewportCoverageRatio (number)・ minZIndex (number)。
framework文字列または nullいいえ 最初に一致した項目の framework。閾値だけが発火したときは "heuristic"。何も取り除かなかったときは null。
removedSelectors文字列の配列いいえ 要素が取り除かれた選択子。selectors の部分集合で、評価した順。
unusableSelectors文字列の配列いいえ ページを読む側が評価できなかった selectors の項目。 これらが何にも当たらなかったのは選択子として成立していなかったからであって、 「当たらなかった」とは別の主張。
removedOverlaysnumberいいえ 選択子ではなく閾値によって取り除かれた要素の数。
devicePixelRationumberいいえ どの読み込みの観測か。devicePixelRatios の項目のいずれか。
unreadabletrueいいえ 除去を試みたが遂行できなかったときに在る。
 
"dismissal": {
  "selectors": [
    { "framework": "OneTrust", "selector": "#onetrust-banner-sdk" },
    { "framework": "Cookiebot", "selector": "#CybotCookiebotDialog" }
  ],
  "heuristic": { "enabled": true, "minViewportCoverageRatio": 0.3, "minZIndex": 1000 },
  "framework": "OneTrust",
  "removedSelectors": ["#onetrust-banner-sdk"],
  "unusableSelectors": [],
  "removedOverlays": 0,
  "devicePixelRatio": 1
}

除去を試みなかった場合、dismissal は存在しては ならない。したがって不在は「配信されたままのページを 保存した」を意味します。「何も見つからなかった」ではありません。

dismissal が在るとき、何も取り除かなかった場合でも selectors と heuristic は在らなければならない。 結果を検証可能にしているのはこの 2 つです —— 20 件の項目の隣に在る空の removedSelectors は「そのどれもが名指しするバナーをページは持たなかった」 と述べますが、項目が 1 件も無い隣の同じ空リストは「何も探さなかった」としか 述べません。1 件も濾さなかった取り込みにも urlPolicies を必須にしているのと 同じ理屈です。

パッケージは unreadable を framework・ removedSelectors・unusableSelectors・ removedOverlays と並べて持ってはならない。 遂行できなかった除去は何も観測しておらず、その隣に空の結果を書くことは 「ページはバナーを持たなかった」という主張になります。

スクロールもまた取り込みが見るものを変えますが、それが何をしたかは既に coverage —— ページのどこまで下れたかを述べるもの —— が記録しています。 同じ行為の 2 つ目の申告をここに置けばそれは写しであり、いずれ片方が 古いほうになります。

ページを 2 回以上読み込む取り込みは、読み込みごとに要素を取り除きます —— 除去は同意ではないので、同意フレームワークは次の読み込みで再び描画されます。 removedSelectors は読み込みをまたいだ和ではなく、ある瞬間の 1 つの文書に対する観測であり、それをどの読み込みのものかに結び付けるのが devicePixelRatio です。

document

browserhive:capture は、ページ由来の記録をどの文書から読んだかを名乗り、 それらを伏せたかどうかを述べる document member を持たなければなりません （MUST）。

ページ由来の記録とは、文書の写し（snapshots を参照）、 取り込んだページのスクリーンショット（screenshots を参照）、 pages/pages.jsonl のエントリの text と title、 datapackage.json の title、 accessibility/axtree.jsonl、logs/capture.jsonl の source が "page" の行（ を参照）、そして random/values.jsonl の行（ を参照）です。これらは ネットワークからではなく描画されたページから読むので、WARC の本文はそれらを縛りません —— 方針が文書の本文を archive に入れなくても、それだけではその文書の文字は 締め出されません。

Member型必須意味
urlstringはい（withheld が "unattributed" のときを除く）browser が確定させた、その文書の URL。"deny" のときは、リクエストを断った URL。隠すシークレットの値は置き換えます（ を参照）。
withheldstringいいえページ由来の記録がパッケージに無い理由。在るときは置かない。
 
"document": {
  "url": "https://example.com/next",
  "withheld": "url-policy"
}

文書とは、ページ由来の記録を読んだ時点で主フレームにあった文書です。 要求した URL の文書とは限りません。サーバのリダイレクトや、ページが自分で行う遷移は 文書を置き換え、記録は置き換わった後のものを記述します。url は、そうした リダイレクトや遷移の後に browser が確定させた、その文書の URL です。

ページ由来の記録は、時点ごとに読みます。ある時点の写しと、それを並べる pages/pages.jsonl のエントリ（ を参照）は、その時点で 主フレームにあった文書から読み、ある時点のスクリーンショットには、その文書が主フレームに 在る間の、取り込んだページが写ります。datapackage.json の title と accessibility/axtree.jsonl は、behavior の後に、document が 名指す文書から読み、"after-behaviors" の時点の写しと、 pages/pages.jsonl の文書のエントリの title と text も同じです。logs/capture.jsonl の source が "page" の行は、ある時点で読むのではなく取り込みの間ずっと書かれるもので、 document が名指す文書から読んだものとして扱います。producer が取り込みの間ずっと、 記録するどの文書でも記録する random/values.jsonl の行も同じです。下の withheld の決まりは、各時点で、その時点の文書に当てはまります: 決まりが文書を 伏せる時点には写しが無く、snapshots はそれを "withheld" と記録します。 その時点のスクリーンショットも在りません（screenshots を参照）。

deny の項目が主フレームの遷移を止めたとき（urlPolicies を参照）、 前の文書を置き換える文書はありません。browser はその場所に誤りのページを表示しますが、 それは取り込みの文書ではありません。このとき文書は遷移が向かっていた先のもので、 url はリクエストを断った URL です。

withheld は、置くなら次のどれかでなければなりません （MUST）。はじめの 4 つは、文書を、あるいはその本文を archive に 入れなかった方針を名指します（ を参照）。

  • "url-policy" —— 文書の URL に最初に当たる urlPolicies の項目の action が no-body。
  • "content-type" —— 文書の URL に当たる urlPolicies の項目が無く、 contentTypePolicies の項目がその media type に当たる。
  • "no-archive" —— 文書の URL に最初に当たる urlPolicies の項目の action が no-archive。パッケージは、その文書を運んだ応答も、その本文も持たない。 持つのは、その要求の withheld request のレコードと、trace の行だけ。
  • "deny" —— 文書の URL に最初に当たる urlPolicies の項目の action が deny。その文書は一度も要求されていない。その時点で読んだ ページ由来の記録は、文書ではなく browser の誤りのページを記述することになる。
  • "unattributed" —— どの文書から記録を読んだかを producer が言えない。 たとえば、読んでいる間に主フレームが遷移した。

producer は、その方針が文書に当たったとき、そしてそのときに限り、 withheld を "url-policy"・"content-type"・ "no-archive"・"deny" にしなければなりません （MUST）。 この決まりは両向きに働きます。リダイレクトの中継だけ、あるいは ページが遷移して離れた文書だけに当たった方針は、何も伏せません。文書に当たった方針は、 要求した URL に当たっていなくても、その記録を伏せます。

withheld を置くとき、パッケージはその文書から読んだページ由来の記録を 持ってはなりません（MUST NOT）。datapackage.json の title はページから読んではならず（MUST NOT）、 パッケージは accessibility/axtree.jsonl を含んではなりません （MUST NOT）。pages/pages.jsonl の文書のエントリ（ を参照）は text と title を持ってはなりません（MUST NOT）。そのエントリは 理由を textWithheld として持ってもよく（MAY）、 持つなら値は withheld と等しくなければなりません （MUST）。文書を伏せたパッケージは、どの時点の スクリーンショットも持たず（screenshots を参照）、random/ の下のエントリも どちらも持ちません（random を参照）。

大きさの上限で落とした本文は、ページ由来の記録を伏せません。上限は取り込みの側の ものであって要求者のものではなく、本文が archive に収まらなかったページこそ、 文字が最も役に立ちます。

snapshots

browserhive:capture は、取り込みが文書を写す時点ごとに、写したかどうかを 述べる配列の snapshots member を持たなければなりません （MUST）。写しは、その時点のページの主フレームの文書の姿を写した もので、WARC に記録されます（[[BROWSERHIVE-WARC-PROFILE]] の Snapshots）。 配列は、"after-load" の項目と、取り込みが behavior を走らせたとき （settings の behaviors が空でないとき）はその後に "after-behaviors" の項目を持たなければならず（MUST）、 ほかの項目は持ちません。

producer が写しを取った時点の項目は、次を持たなければなりません （MUST）:

Member型必須意味
stagestringはい 時点: "after-load" か "after-behaviors"。
urlstringはい 写しの resource レコードの WARC-Target-URI。
datestringはい そのレコードの WARC-Date。タイムスタンプ。
recordstringはい そのレコードの WARC-Record-ID の URI。その欄が付ける山括弧は 付けません。
bytesnumberはい 写しの大きさ（バイト）。そのレコードの Content-Length。
secretsReplacednumberはい producer が写しの中でシークレットの値を置き換えた回数。写しの metadata レコードの secrets-replaced。
 
"snapshots": [
  {
    "stage": "after-load",
    "url": "urn:browserhive:snapshot:after-load:https://example.com/",
    "date": "2026-11-02T01:20:05.118Z",
    "record": "urn:uuid:5e0f6a3c-2d7b-4f1e-9a8c-1b2d3e4f5a6b",
    "bytes": 7255,
    "secretsReplaced": 0

producer が写しを取らなかった時点の項目は、stage と skipped だけを持たなければなりません（MUST）—— たとえば {"stage": "after-behaviors", "skipped": "too-large"}。skipped は次のどれかでなければなりません（MUST）:

  • "withheld" —— document の withheld の決まりが、 その時点の文書を伏せる。あるいは、それがどの文書だったかを producer が言えない。
  • "too-large" —— 写しが、producer が 1 つの写しに許す大きさを超えた。
  • "task-budget" —— 写しを残すと、取り込みが残すバイト数が limits.maxTaskBytes（settings を参照）を超えるところだった。 レスポンスの本文やスクリーンショットと分け合う上限です。
  • "failed" —— producer が写しを取ろうとして、取れなかった。

パッケージは、項目が名指す写しをすべて持たなければならず、どの項目も名指さない写しは 持ちません（MUST）。

パッケージに無い写しは、伏せたのか、大きすぎたのか、失われたのかが分からず、取り込みに その時点がそもそも無かったのかもしれません。項目はそのどれかを述べるので、読み手は、 取り込みが入れないと決めたページを、写し損ねたページと取り違えません。

screenshots

browserhive:capture は、取り込みが文書を写す時点（snapshots を参照） ごとに、パッケージがその時点のスクリーンショットを持つかどうかと、持たないときはその理由を 述べる配列の screenshots member を持たなければなりません （MUST）。スクリーンショットは、その時点に browser が見せていた、 取り込んだページの画像で、WARC に 2 つのレコードで記録されます（[[BROWSERHIVE-WARC-PROFILE]] の Screenshots）: 画像を持つ resource レコード —— その WARC-Target-URI は urn:browserhive:screenshot: で始まります —— と、その画像が何であるかを述べる metadata レコードです。配列は、"after-load" の項目と、 取り込みが behavior を走らせたとき（settings の behaviors が空でない とき）はその後の "after-behaviors" の項目だけを持たなければなりません （MUST）。

スクリーンショットに写るのは、そのときまでに取り込みが手を入れた後の、取り込んだページです。 取り込みが記録の前にそのページから何かを取り除いていれば、画像にはそれが無いページが写り、 何を取り除いたかは dismissal が述べます。

スクリーンショットを撮るかどうかは producer が選ぶことで、本プロファイルは撮ることを 求めません。求めるのは、スクリーンショットがどうなったかをパッケージが述べることと、 取り込みがパッケージに入れないよう求められたものを画像が写しうるときに、パッケージが スクリーンショットを 1 枚も持たないことです（下を参照）。

パッケージがスクリーンショットを持つ時点の項目は、次の member を持たなければならず、 skipped は持ちません（MUST）:

datestringはい そのレコードの WARC-Date。タイムスタンプ。
recordstringはい そのレコードの WARC-Record-ID の URI。その欄が付ける山括弧は 付けません。
bytesnumberはい 画像の大きさ（バイト）。そのレコードの Content-Length。

スクリーンショットに写るのは viewport —— 取り込んだページのうち browser が見せていた 部分 —— で、その先は写りません。取り込みの viewport は settings が記録するもので、 画像の大きさと、そのときの device pixel ratio は、スクリーンショットの metadata レコードが述べます。

パッケージがスクリーンショットを持たない時点の項目は、stage と skipped だけを持たなければなりません（MUST）—— たとえば {"stage": "after-load", "skipped": "withheld"}。 skipped は次のどれかで、いくつも当てはまるときは、この並びで先に来るもので なければなりません（MUST）:

  • "disabled" —— producer が、スクリーンショットを撮る設定になっていなかった。
  • "secret" —— 取り込みがシークレットを渡された。settings の secrets が空でない。
  • "withheld" —— 取り込みの方針か、文書の成り行きが、スクリーンショットを 外す（下を参照）: 取り込みがメディア型の方針を持っていた。urlPolicies の no-archive か no-body の項目が、文書・画像・メディアの要求に、 またはパッケージが種類を示せない要求に当たった。取り込みの終わりに、またはその時点で、 文書が伏せられている。あるいは、その時点の画像がどの文書を写しているかを producer が 言えない。
  • "task-budget" —— 画像を残すと、取り込みが残すバイト数が limits.maxTaskBytes（settings を参照）を超えるところだった。 スクリーンショットが、レスポンスの本文や写しと分け合う上限です。
  • "failed" —— producer がスクリーンショットを撮ろうとして、撮れなかった。 あるいは、先の 1 枚を諦めた後で、試さなかった（下を参照）。

したがって、項目が "secret" を持つのは secrets が空でない パッケージだけで、そういうパッケージでは、どの項目も "disabled" か "secret" を持ちます。

パッケージは、項目が名指すスクリーンショットをすべて持たなければならず、どの項目も 名指さないスクリーンショットは持ちません（MUST）。

画像は、文字のようには直せません。producer は、スクリーンショットのピクセルの中から、 値も、方針が伏せた画像も見つけられず、そこだけを取り除いて残りを残すこともできません。 だから、取り込みがパッケージに入れないよう求められたものを画像に入れない手は、画像を 残さないことだけです。パッケージは、次のどれかが当てはまるとき、どの時点の スクリーンショットも持ってはなりません（MUST NOT）:

  1. settings の secrets が空でない。取り込んだページは、シークレットの 値を見せることがあります —— behavior が値を打った欄や、オリジンが返したものの中に。 これは、隠すシークレットにも残すシークレットにも当てはまります: シークレットを残すと、 wire を渡ったものの記録に値が残りますが、取り込んだページから読むものでは、残す値も置き換えます （ を参照）。画像では、それができません。
  2. settings の contentTypePolicies が空でない。メディア型の方針は、 応答のメディア型で応答に当たります。メディア型は応答が届いてからしか分からず、producer は、 取り込んだページが見せた応答の全部のメディア型を見るわけではありません —— 別サイトの フレームの中の応答と、取り込みの終わりまでに届かなかった応答は見えません。 だから producer には、そうした方針が入れないはずだった本文を どの画像も写していない、とは言えません。BrowserHive は自前のメディア型の方針を 持たないので、当てはまるのは、その方針を設定された取り込みだけです。
  3. document が withheld を持つ。ページ由来の記録についての document の決まりを、もう一歩進めたものです: パッケージは、前の時点の スクリーンショットも持ちません。どの文書が書いた行であれ、取り込んだページがログに 書いた行を持たないのと同じです。
  4. archive/ の WARC ファイルが、action が no-archive の withheld request のレコードを持ち、 そのレコードの resourceType が Document・Image・ Media のどれかであるか、そのレコードが resourceType を 持たない。
  5. archive/ の WARC ファイルが、truncated が url-policy の body not kept のレコードを持ち、 そのレコードが指す response レコードを record で名指す trace/events.jsonl の行（ を参照）の resourceType が Document・Image・ Media のどれかであるか、その行が resourceType を持たない。 あるいは、その response レコードを名指す行が無い（producer が trace から 行を省いたときなど）。応答の status は問いません: body not kept のレコードが リダイレクトのものであれば、それも、ほかの応答のものと同じに数えます。

上の 4 番目と 5 番目の条件では、urlPolicies の no-archive か no-body の項目が、文書・画像・メディアの要求に当たっています。 方針は要求に当たるもので、producer は、応答がどうなるかを知る前に、要求の時点で決めます。 そのため、取り込んだページに見せる本文が応答に在ったかどうかは問わず、条件はリダイレクトの 中継にも当てはまります。これは、document が引く線 —— リダイレクトの中継だけに 当たった方針は何も伏せない —— とは別の線です: スクリーンショットは、1 つの文書に ついてではなく、取り込みの全体について決めるからです。

Document・Image・Media は、レコードや行の resourceType の値と、1 文字ずつ比べます。これらは browser の語で、 本プロファイルは定義しません（ を参照）。browser がほかの語を 使う producer は、この 3 つが指す要求 —— 文書（フレームの文書を含む）の要求、画像の要求、 音声や動画の要求 —— を同じに扱います。

ある時点のスクリーンショットは、その時点で主フレームにあった文書を写します。パッケージは、 document の決まりが文書を伏せる時点のスクリーンショットも、撮っている間に 主フレームの文書が替わったために、どの文書を写しているかを producer が言えない スクリーンショットも、持ってはなりません（MUST NOT）。 snapshots が "withheld" と記録する時点の項目は、 skipped を持たなければなりません（MUST）。

4 番目と 5 番目の条件の後ろには、producer を縛る決まりが在ります。 producer は、ある要求の URL に最初に当たる urlPolicies の項目の action が no-archive か no-body で、producer が読むその要求の報告の どれかで、browser がその要求を Document・Image・ Media と伝えた取り込みのスクリーンショットを、残してはなりません （MUST NOT）。browser は、1 つの要求を 2 か所以上で、同じでない語で 伝えることがあります: Chromium は、動画の字幕の要求を、producer が要求を止める所では Media、記録する所では TextTrack と呼び、object や embed の要素が読み込む画像を、Other と Image と 呼びます。そうした報告が 1 つ在れば足ります。 この決まりは、その要求がどうなったか —— 応答を本文なしで記録した、リダイレクトされた、 失敗した、取り込みの終わりまでに応答が届かなかった —— には関わらず、取り込んだページの どこが要求を出したかにも関わりません。producer がレコードを書かない、別サイトの フレームの中も入ります。

その 2 つの条件と、この決まりは、同じ取り込みを覆うわけではありません。2 つの条件は、 要求の種類をパッケージが示せないときにも当てはまります: レコードや行が resourceType を持たないとき、producer がその行を trace から省いたときです。 producer は、browser が何と伝えたかに関わらず、そうした取り込みのスクリーンショットも 残さず、項目は "withheld" を持ちます。逆の向きでは、パッケージを読む道具に、 この決まりが届く要求の全部は見えません。producer がレコードを書かなかった要求 —— 別サイトのフレームの中で出された要求、no-body の項目が当たって応答が 届かなかった要求、送る本文の無い応答が返った要求（[[BROWSERHIVE-WARC-PROFILE]] は、 その応答にそのレコードを求めません）—— は見えません。レコードが、数えられた報告とは 別の語で要求を呼んでいるときも、その要求が数えられたことは見えません。そのとき項目は "withheld" を持ち、パッケージのほかのどこも、その理由を述べません。

deny の項目は外しません: 送られなかった要求は、取り込んだページに見せるものを 何も運んでいません。その項目が主フレームの遷移を止めたときは、文書の場所に browser の 誤りのページが在り、document が withheld を持ちます。大きさの上限で 落とした本文も外しません。理由は、ほかのページ由来の記録を伏せないのと同じです （document を参照）: 上限は取り込みの側のもので、要求者のものではありません。 ほかの種類だとパッケージが示す要求 —— スクリプトやスタイルシートの要求など —— に だけ当たり、その要求を、producer が読んだどの報告も文書・画像・メディアと呼ばなかった urlPolicies の項目も外しません。それが画像に何を残すかは、 に書きます。

producer には、どの画像がどの応答を写しているかが分かりません。browser は、取り込んだ ページが応答を見せるよりずっと前に、その応答を持っていることがあるからです。そのため、 条件は取り込みの全体を見ます。方針が、画像を撮った後に出された要求に当たることも あります —— viewport より下の画像は、behavior がそこまで scroll して初めて要求されます。 だから producer は、記録を止めるまで画像を持っておき、そのときにまとめて書くか、まとめて 捨てることになります。先に WARC ファイルへ書いた画像は、取り出せません。

[[BROWSERHIVE-WARC-PROFILE]] は、スクリーンショットに、producer が撮り始めたときの viewport の大きさ・device pixel ratio・scroll の位置のままの、取り込んだページを 写させます。だから producer は、画像のためにそのどれも変えません。パッケージでは、これが、 取り込みが画像より後に記録したものの全部について、settings を正しいままにします: そのページは、settings が挙げる viewport と、device pixel ratio のどれかの下で先へ 進んでいます。取り込んだページが変えられたかどうかは、パッケージを読む道具には見えません。

main thread を手放さないページは、取り込みが待てるより長く、browser に画像を 渡させないことがあります。producer は、自分の決めた時間の後でスクリーンショットを 諦めてよく（MAY）、1 枚を諦めた producer は、その取り込みの その後のスクリーンショットを試さなくてもかまいません（MAY）。 producer は、そのどれも "failed" と記録します。

スクリーンショットは、pages/pages.jsonl にエントリを持ちません。読み手が 開くページではないからです（ を参照）。その resource レコードは CDXJ 索引に在り（ を参照）、読み手は、項目の url と date でそれを見つけます。

この版に適合するパッケージが持つ項目は、上の 2 つの時点のものだけです。本プロファイルの 後の版は、別の種類の項目 —— 時点で撮るのではないスクリーンショットの項目 —— を 足すことがあり、[[BROWSERHIVE-WARC-PROFILE]] はそのための余地を残しています。

スクリーンショットの無いパッケージは、撮らない producer のものかもしれず、画像を 残せなかった取り込みのものかもしれず、撮れなかった取り込みのものかもしれません。項目は そのどれかを述べるので、読み手は、取り込みが残してはならなかった画像を、撮り損ねた画像と 取り違えず、取り込みを見せる道具は、画像が無い理由を言えます。

trace

browserhive:capture は、取り込みの trace が何行を持ち、producer がそこから 何行を残さなかったかを述べる trace member を持たなければなりません （MUST）。trace そのものは、エントリ trace/events.jsonl です（ を参照）。

Member型必須意味
linesnumberはい trace/events.jsonl の行の数。0 以上の整数。
droppednumberはい producer が作り、その後、trace を自分の決めた上限に収めるためにそのエントリに 残さなかった行の数（ を参照）。0 以上の整数。
 
"trace": {
  "lines": 44,

残さなかった行は、エントリに跡を残しません。そのため、間の抜けた trace は、全部そろった trace と同じように読めます。パッケージがそのどちらを持つのかを述べる場所がこの member で、 読み手は、エントリを開く前に、datapackage.json だけでそれを見分けられます。

random

browserhive:capture は、取り込んだページのスクリプトが乱数として受け取った値を パッケージが持つかどうかと、それを何行が持つか、持たないならその理由を述べる random member を持たなければなりません（MUST）。 値そのものは、エントリ random/values.jsonl に在ります （ を参照）。

Member型必須意味

recorded が false のとき、random は skipped を持たなければならず（MUST）、 documents・draws・truncated を持ってはなりません （MUST NOT）—— たとえば {"recorded": false, "skipped": "not-requested"}。 skipped は次のどれかで、いくつも当てはまるときは、この並びで先に来るもので なければなりません（MUST）:

  • "not-requested" —— 取り込みは、値の記録を求められていなかった。
  • "withheld" —— 文書が伏せられた: document が withheld を 持つ。random/values.jsonl の行はページ由来の記録で、文書を伏せたパッケージは それを持ちません。

random/ の下にエントリを持たないパッケージは、取り込みが記録を求められなかった のか、文書が伏せられたのか、記録に失敗したのかを問わず、同じに読めます。間の抜けたエントリも、 全部そろったエントリと同じように読めます。パッケージがそのどれなのかを述べる場所がこの member で、読み手は、どのエントリを開く前にも、datapackage.json だけで、 パッケージが記録した値を持つかどうかを見分けられます。

BrowserHive は、取り込みの要求がその欄 recordRandom で求めたときに値を記録します。 その recorder は、取り込んだページのスクリプトが Math.random・ crypto.getRandomValues・crypto.randomUUID から受け取る値を、 変えずに、呼んだスクリプトと共に書き留めます。ページを replay する読み手は、同じ値を同じ スクリプトに返せます。そうすれば、見せるものを乱数で選ぶページは、取り込みのときに選んだ ものを選びます（ を参照）。

chainRefstringいいえtls.chains への鍵。チェーンを取得できなかったときは存在しない。

HTTPS で到達したが接続が何も明かさなかった host は、値 null として記録され なければならない。鍵ごと省くと「この host は素の HTTP だった」と 読めてしまいますが、それは別の事実です。

host 名の照合に使われるのは subject ではなく san です。 subject が記録するのは common name であり、現在の読み手はこれを照合に 用いません —— subject の値をもって「その host 名で通用した」と読んでは ならない。

chainRef が無いことを「この host は証明書を提示しなかった」と読んでは ならない。チェーンの取得は host と無関係な理由でも失敗します。

Package name

[[WACZ]] は、それに従う ZIP ファイルが拡張子 .wacz を使うことを求めます。 producer は BrowserHive WACZ に .browserhive.wacz で終わる名前を付ける べきである（SHOULD）。[[WACZ]] が求める拡張子の前に 印を置き、ファイルを手にした人やプログラムが、開く前にそれが何かを分かるようにするためです。

印は手がかりであって、名乗りではありません。パッケージは写しのたびに名前を保ちも失いもし、 誰でもファイルにどんな名前でも付けられます。適合するパッケージは、.wacz で終わる 別の名前でも、印の有無にかかわらず適合し続け、印のある名前は何も証しません （ を参照）。

Archive files

[[WACZ]] は archive/ ディレクトリに 1 本以上の WARC ファイルを置くこと （GZIP で圧縮したものは拡張子 .warc.gz、圧縮しないものは望ましくは .warc）を 求め、名前についてそれ以外のこと、数、それぞれが何を持つかについては何も述べません。この節は名前と数を定めます。 読み手が、producer の書いたファイルをパッケージが全部持っているかを判定でき、producer が 1 本のファイルの大きさを抑えられるようにするためです。それぞれのファイルが何を持つかは [[BROWSERHIVE-WARC-PROFILE]] が定めます。

archive/ のどの WARC ファイルも BrowserHive WARC Profile 1.4.0 に適合し なければならず、その warcinfo レコードは conformsTo でその版を名乗らなければならない （同仕様の The warcinfo record を参照）。レコードについては 同仕様が定めます —— ペイロード、隠すシークレットの値を置き換えるレコード、 body not kept・withheld request・window not opened の レコード、文書の写しと取り込んだページのスクリーンショット、各ファイルの先頭の warcinfo レコード、1 つの交信のレコード・1 つの写しのレコード・1 つの スクリーンショットのレコードが、それぞれ同じファイルに入ること。

archive/ ディレクトリは、data-NNN.browserhive.warc.gz という名前の ファイルだけを含まなければならない。NNN は 10 進 3 桁で、 000 から飛びなく番号を振ります。レコードが 1 本に収まる取り込みは、ちょうど data-000.browserhive.warc.gz を持ちます。名前は [[WACZ]] が求める拡張子の前に 印 browserhive を置きます。パッケージから取り出した WARC ファイルも、名前で BrowserHive WARC ファイルと 分かるようにするためです。パッケージの名前と同じく（ を参照）、 印は手がかりであって、名乗りではありません。

archive/ の各 WARC ファイルは GZIP で圧縮されていなければならない。 [[WACZ]] が、.warc.gz という名前のファイルにそれを求めるからです。

ファイルが warcinfo レコードの WARC-Filename に書く自分の名前は、 ディレクトリを付けない、archive/ の中での名前で なければならない（data-000.browserhive.warc.gz であって archive/data-000.browserhive.warc.gz ではない）。

producer は、いまのファイルが maxWarcBytes バイト以上のとき、次の交信を書く前に 新しいファイルを始めなければならない（settings を参照）。 したがって最後のファイルを除くすべてのファイルは maxWarcBytes バイト以上で なければならず、ファイルがそれを超えるのは交信 1 つ分までで あってよい。

CDXJ の各行の filename field は、archive/ からの相対でファイルを 名指さなければならない（data-001.browserhive.warc.gz であって archive/data-001.browserhive.warc.gz ではない）。読み手はディレクトリを自分で前置します。

[[BROWSERHIVE-WARC-PROFILE]] が定める metadata レコード —— body not kept・ withheld request・window not opened のレコード —— は、パッケージの CDXJ 索引に現れることを 要求されません。これを探す読み手は WARC を読みます。

写しの resource レコードと、スクリーンショット（screenshots を参照）の resource レコードは、どれも CDXJ 索引に現れなければなりません （MUST）。アーカイブしたページを配る読み手は、索引で写しを 見つけ、スクリーンショットを見せる読み手は、WARC ファイルを読み通さずに画像を 見つけるからです。その行の検索の鍵は、レコードの WARC-Target-URI そのまま —— SURT の形を持たない urn:browserhive:snapshot: か urn:browserhive:screenshot: の URI —— でなければならず （MUST）、行の JSON は status を持ってはなりません （MUST NOT）。どのサーバもステータスで答えていないからです。写しと スクリーンショットの metadata レコードは、上のレコードと同じく、現れることを 要求されません。 

archive/data-000.browserhive.warc.gz    warcinfo (WARC-Filename: data-000.browserhive.warc.gz), exchanges …
archive/data-001.browserhive.warc.gz    warcinfo (WARC-Filename: data-001.browserhive.warc.gz), exchanges …
indexes/index.cdxj                      … {"filename":"data-001.browserhive.warc.gz","offset":"153","length":"2048",…}

リンクを辿る取り込みは、クロールが続く限り記録し、それとともに育つ 1 本のファイルは、 一部だけを読むことも、一部だけを検証することも、プロセスが死んだとき一部だけを無事に 残すこともできません。ファイルを抑えれば、閉じたファイルはどれも完全なまま残り、読み手は 手前を読まずに索引からパッケージの中へ seek できます。上限が本プロファイルの定数ではなく producer の設定なのは、ちょうどよい大きさが、パッケージを置き読む場所に依るからです。 他所の慣習は 1 ギガバイトです。

Pages

[[WACZ]] はパッケージのページを pages/pages.jsonl に並べ、アーカイブした ページを配る読み手は、エントリの url と ts でページを開きます。 この節はそのエントリを定め、取り込みを求められた文書と、そのどの写し（snapshots を 参照）も、ページとして開けるようにします。

pages/pages.jsonl の最初のエントリは、文書のエントリでなければなりません （MUST）。その後に、写しごとに 1 つのエントリを snapshots の順に持たなければならず、ほかのエントリは持ちません（MUST）。 文書のエントリは:

  • url が、取り込みを求められた URL を、URL Standard の URL serializer が書くとおりに書き、fragment を除いたもので なければなりません（MUST）。これは、取り込みが文書のために出した 最初の要求の URL です。path が空の URL には、要求と同じく末尾の / が付きます。 producer は URL に隠すシークレットの値を持つ要求を断り、残すシークレットの値は URL に残ります（ を参照）。
  • ts は、取り込みを始めた時刻です。
  • stage を持ってはなりません（MUST NOT）。
  • id が、ほかのどのエントリのものとも違わなければなりません （MUST）。
  • title と text は、在るなら、behavior の後に、document が名指す文書から読みます。

写しのエントリは:

  • url と ts が、写しの resource レコードの WARC-Target-URI と WARC-Date でなければなりません （MUST）。
  • stage が、写しの時点でなければなりません（MUST）。
  • id が、ほかのどのエントリのものとも違わなければなりません （MUST）。読み手は、id が同じエントリを 1 つだけ 残し、ほかを捨てます。
  • title と text は、在るなら、その時点の文書から読みます （document を参照）。

datapackage.json の mainPageURL は、pages/pages.jsonl の最初のエントリ、つまり文書のエントリの url と同じでなければなりません （MUST）。 

{"format":"json-pages-1.0","id":"pages","title":"All Pages"}
{"id":"5f2c9a1e","url":"https://example.com/","ts":"2026-11-02T01:20:03.502Z","title":"Results for lamp","text":"3 results …"}
{"id":"5f2c9a1e-after-load","url":"urn:browserhive:snapshot:after-load:https://example.com/","ts":"2026-11-02T01:20:05.118Z","stage":"after-load","title":"Search","text":"Search the shop …"}
{"id":"5f2c9a1e-after-behaviors","url":"urn:browserhive:snapshot:after-behaviors:https://example.com/results","ts":"2026-11-02T01:20:07.415Z","stage":"after-behaviors","title":"Results for lamp","text":"3 results …"}

写しは、頁の script を除いた文書の DOM の写しです。そのため、script が出すもの —— アニメーションが終わってから置かれる絵や、要求で埋まる一覧 —— が、写しに無いことがあります。 文書のエントリは、記録した応答を頁の script を動かして開き、最初に見えた頁を出します。 文書を記録したなら、取り込みを求められた URL は記録を名指します: 文書を返した応答か、 そこへ導いた転送で、読み手は転送を辿ります。

どこから開くかは、読み手によって違います。mainPageURL を開く読み手もいれば、 エントリを新しい順に並べ、文書を最後に置く読み手もいます。読み手に文書を見せたいリンクは、 その url と ts を名指します。

URL and media type policies

取り込みは、一部のリクエストを他と違う扱いにすることがあります —— 送らない、記録しない、本文なしで記録する。 browserhive:capture.settings は何をしたかを MUST 記録します。取り込みの設定に手が届かない読み手が、 そのどれであったかを判定できるようにするためです。

方針が働くのはネットワークの本文です。描画されたページから読む記録 —— ページの文字・ 題・アクセシビリティツリー —— に方針が何をするかは、document で定め、取り込んだ ページのスクリーンショットに何をするかは、screenshots で定めます。

urlPolicies

urlPolicies は順序付きの配列です。各項目は 2 つの member を持つ オブジェクト:

MemberType必須説明
patternstringはい 効いていたパターン。取り込みが設定されたとおりの綴りで。

pattern は、リクエストの URL 全体に当てます。* は 0 字を含む 任意の文字の並びに当たり、ほかの文字は ? も含めてその字だけに当たり、 大文字と小文字は区別します。そのため、パターンは query を見込んで書く必要があります —— *://example.com/a.js は https://example.com/a.js?v=2 に 当たりません。

取り込みは、シークレットの値を置き換える前の URL にパターンを当てます （ を参照）。そのため、シークレットの名前を持つパッケージでは、 *** を持つ URL は、取り込みが適用した項目と別の項目に当たることも、 どの項目にも当たらないこともあります。読み手は、そのような URL に当てた結果を、 取り込みがしたこととして受け取ってはなりません（MUST NOT）。

actionリクエストの送信パッケージが持つもの
denyしない WARC の中のリクエストの記録と、trace の行（ を参照）。 その URL について取り込みを行った機械から 出たものは無く、それを通じて取り込みを知ったオリジンも在りません。
no-archiveする WARC の中のリクエストの記録と、trace の行。取り込みは要求を送らせましたが、 パッケージは、その交信のほかの何も保持しません。
no-bodyする request / response のレコード。ただし response の本文は含みません。

deny と no-archive の項目が残す記録は、 withheld request のレコード （[[BROWSERHIVE-WARC-PROFILE]]）です。その action は項目の action で、pattern は、読み手が項目を見つけられるよう、項目の pattern をここに現れるとおりの綴りで書かなければならない。 no-body の項目はこの記録を残しません。交信はいつもどおり記録され、無い本文は truncated が url-policy の body not kept のレコードが述べます —— サイズ上限で落とした本文としては扱いません（completeness を参照）。

deny の項目は、ページのどの部分が起こしたかに関わらず、取り込みが起こす すべてのリクエストに働きます。主フレームの遷移（サーバのリダイレクトの先と、script が 始めた遷移を含む）、フレーム（別サイトのフレームを含む）、そして dedicated worker と service worker です。これらのリクエストの 1 つでも取り込みを行う機械から出した producer は、その項目を守っていません。取り込みの間、ページはウィンドウを開きません （ を参照）。項目が届くべきウィンドウはありません。

最初の遷移に deny の項目が当たった取り込みは、パッケージを作っては なりません（MUST NOT）。何も読み込まれていないので、 settle の報告は走らなかった待ちを記述することになります。ページを読み込んだ後に 遷移を断られた取り込みは、パッケージを作ってもよく（MAY）、 その document は withheld: "deny" を持ちます。

WebSocket の handshake は、ほかのリクエストのようには止められません。URL に deny の項目が当たる WebSocket を開いた取り込みは、パッケージを作っては なりません（MUST NOT）。リクエストは送られており、 パッケージはそうでないと主張することになるからです。

この配列は空のときでも存在して MUST、 空の配列は「効いていた policy が無い」という意味で MUST。この規則が無いと読み手は、 特別なものを何も要求しなかったページと、要求されたものを記録しないことにした 取り込みとを区別できません。同じパッケージについての、別の主張です。

順序は取り込みがパターンを評価した順であり、取り込みは 一致した最初の項目を適用して MUST。 順序を記録することが、複数のパターンが当たりうる URL について 「どの policy が適用されたのか」に読み手が答えられる根拠になります。 

"urlPolicies": [
  { "pattern": "*://cdn.example.com/tracker.js", "action": "deny" },
  { "pattern": "*://cdn.example.com/*",          "action": "no-body" }
]

この例では tracker.js へのリクエストは一度も送られず、 同じホストの他のものは取得されて本文なしで記録されます。2 つを入れ替えると 取り込みがしたことが変わります —— 広いほうのパターンが先に当たり、 tracker は取得されます。

contentTypePolicies

contentTypePolicies は、prefix （応答のメディア型に当てる）と action を持つ項目の配列です。 この版が定める action は no-body のみ —— メディア型は応答が届いてからしか分からないので、deny は 適用できません。

この配列も、空のときでも存在して MUST。 理由は urlPolicies と同じです。この配列が空でないパッケージは、 スクリーンショットを持ちません（screenshots を参照）。 

"contentTypePolicies": [
  { "prefix": "video/", "action": "no-body" }
]

Windows the page asks for

取り込みは 1 つのページを記録します。取り込みの間、producer はページに新しい top-level browsing context —— ウィンドウやタブ —— を与えてはなりません （MUST NOT）。誰が求めても同じです: ページ自身の script、 その中のフレーム、取り込みのリクエストが運んだ script。ページへの答えは、browser が popup を止めたときと同じです: window.open は null を返し、 新しいウィンドウを target にした link や form は何も開きません。

ページが求めた 1 回ごとに、WARC には window not opened のレコード （[[BROWSERHIVE-WARC-PROFILE]]）が残ります。ウィンドウの文書のリクエストは送られて いないので、このレコードは urlPolicies の項目が URL に当たるかどうかに関わらず 書かれ、withheld request のレコードではありません。

それでもウィンドウが開いた取り込みは、パッケージを作ってはなりません （MUST NOT）。ウィンドウのリクエストはパッケージに現れない まま相手のオリジンに届いており、パッケージは何も開かなかった取り込みとして自らを 記述することになるからです。

browser がウィンドウを開くのは、user activation —— 人の click や打鍵の痕跡 —— を 持つページに対してだけです。BrowserHive はそれをページに与えません。ページで評価する コードは、リクエストが運ぶ behaviors と preload の script を含めて、activation なしで 走ります。ウィンドウを断るのはこれです。それらの script が、window.open・ Fullscreen API・clipboard への書き込みのような gesture の要る API を使えないのも、 同じ理由です。

Values of secrets

要求は、behavior に読ませる値を秘密として渡すことができ、settings がその名前を記録します。 behavior はその値をネットワークへ送ることができ、ページはそれを表示できるので、 取り込みは記録するものの中でその値に出会います。[[BROWSERHIVE-WARC-PROFILE]] の Redacted records の節が、シークレット・隠すシークレット・出現・redacted のレコード・文字の本文という 語を定め、1 本の WARC ファイルがそれらをどう扱うかを述べます。この節は、パッケージの シークレットのどれを隠すのかと、パッケージの残りがそれらをどう扱うかを述べます。

secrets の名前はどれも、シークレットを名指します。secretArchive が 名指すものが 残すシークレットで、ほかは隠すシークレットです。

この節の決まりが値を置き換えるのは、値が文字かバイト列として在る所です。 スクリーンショット（screenshots を参照）は画像です: 取り込んだページが見せた値を 写しえますが、そのバイト列の中に、producer が見つけて置き換えられる出現はありません。 そのため、secrets が空でないパッケージは、シークレットを隠すか残すかに 関わらず、スクリーンショットを持ちません。

Requests a producer refuses

要求によっては、この節の決まりを破らずには実行できません。producer は次の要求を 断らなければならず（MUST）、それらのためにパッケージを作っては なりません（MUST NOT）:

  • 隠すシークレットに 8 文字より短い値を渡す要求。そんなに短い値を置き換えると、 無関係の文字にも届きます。要求は、代わりにその値を残すことを求められます。
  • 隠すシークレットの値の出現を持つ URL の取り込みを求める要求。 pages/pages.jsonl の最初のエントリと mainPageURL はその URL で （ を参照）、読み手はそれで文書を開くので、置き換えられません。
  • 隠すシークレットを持ち、パッケージに storage/origins.jsonl を持たせることに なる要求。そのエントリは area が保持していたとおりの値を持ち、ページは behavior から 受け取ったものを保存できます（ を参照）。

Hidden secrets

パッケージは、隠すシークレットの値の出現を、どのファイルにも持ってはなりません （MUST NOT）: datapackage.json、 datapackage-digest.json、展開した後の archive/ の WARC ファイル、 およびほかのどのエントリにも。[[BROWSERHIVE-WARC-PROFILE]] はこれを 1 本の WARC ファイルに ついて述べ、パッケージの残りについては述べようがありません。

本仕様がパッケージに URL を記録させる所では、producer はその中の出現を 3 文字の *** に置き換えなければならず（MUST）、 同仕様が WARC-Target-URI を URI のままにするように、結果は URL のままです。 置き換えると URL の scheme が無くなるときは、producer は結果の前に元の scheme とコロンを書きます。 値が port の中から始まるときなど、それでも URL にならないときは、scheme とコロンと *** だけを書きます。対象は次のものです:

  • document の url。
  • bodylessUrls・truncatedUrls・uninterceptedUrls の URL と、crashedTargets の url（completeness を参照）。
  • accessibility/axtree.jsonl の各行と各ノードの url。
  • CDXJ の索引の各行の url と searchable key。url は、その行が名指す レコードの WARC-Target-URI で、key は置き換えた後のそれから作ります。
  • snapshots の url と、写しを挙げる pages/pages.jsonl の エントリの url。これらは写しの resource レコードの WARC-Target-URI で、そこでシークレットの値は既に置き換えてあります。
  • random/values.jsonl の各文書の行の url と、各値の行の caller（ を参照）。

これらの URL を整列する配列は、置き換えた後の、書かれたとおりの字で整列します。 置き換えで 2 つの URL が同じになることがあり、URL を 1 度だけ挙げる配列は、その URL を 1 度だけ挙げます。置き換えた URL には印が無く、読み手はそこの *** と URL の中の 同じ字とを区別できません。

producer は、pages/pages.jsonl のエントリの text と title、 datapackage.json の title、 accessibility/axtree.jsonl のノードの name と value、 logs/capture.jsonl の行の msg と data （ を参照）、trace/events.jsonl の行の url・initiator の url・error （ を参照）でも、出現を *** に 置き換えなければなりません（MUST）。 trace の行の url と、その initiator の url は、 上に挙げた URL には入りません: producer は文字と同じように置き換え、そこに書いたものが URL のままであるとは限りません。切った URL、data: の URL の書き方、 残すシークレットの置き換えは、URL の形を保たないことがあるからです。

WARC ファイルの外では、パッケージのほかのものは何も置き換えません: behavior と preload のスクリプトの source、behaviors/runtime.js、 random/recorder.js、 variables や urlPolicies の項目、tls の host、storage の origin、 trace/events.jsonl と random/values.jsonl の行のほかの member、 member の名前。これらのどこかに出現を書くことになる取り込みは、パッケージを作っては なりません（MUST NOT）。

[[BROWSERHIVE-WARC-PROFILE]] は、ある種の cookie の値を、その cookie を設定した応答が届いた 瞬間から、隠すシークレットの値として producer に扱わせます。その値は secrets に 名前を持ちません。その瞬間から、producer は、この節が出現を置き換えさせる所でその値を 置き換えなければなりません（MUST）。それ以上は求めません: それより前に producer が受け取ったものや書いたもの、pages/pages.jsonl の最初の エントリのように取り込みの要求から写すもの、置き換えないものは、その値を持っていることがあります。

Kept secrets

要求がシークレットを残すのは、wire を渡ったものを読み手が見られるようにするためです。 残すシークレットの値は、写しのレコードを除き、WARC の request・ response・metadata のレコードに残ります。そうした交信と文書について パッケージが記録する URL にも残ります: document の url、 accessibility/axtree.jsonl の各行の url、completeness の URL、 応答の CDXJ の行の url と searchable key です。取り込みを求められた URL が値を 持つときは、その URL に残ります: pages/pages.jsonl の最初のエントリ、 mainPageURL、そして producer がその URL を書くなら、warcinfo レコードの description と datapackage.json の title です。 が置き換えないと述べるものと、area が保持していたとおりの 値を持つ storage/origins.jsonl にも残ります。

パッケージは、残すシークレットの値を、そのままの形で、長さに関わらず、次のどこにも持っては なりません（MUST NOT）。producer はそこでは値を *** に 置き換えます。

  • 写しと、その URL（[[BROWSERHIVE-WARC-PROFILE]]）。
  • pages/pages.jsonl のエントリの text と title、および ページから読んだときの datapackage.json の title。
  • accessibility/axtree.jsonl のノードの name・value・ url。
  • logs/capture.jsonl の行の msg と data。
  • trace/events.jsonl の行の url・initiator の url・error（ を参照）。
  • random/values.jsonl の文書の行の url と、値の行の caller（ を参照）。

残す値が、隠すシークレットの値である、または持つときは、その値の分は置き換えます。 WARC のレコードでも、隠すシークレットの決まりが先です。

シークレットを残すのは、何が送られ何が返ったかを読み手が見られるようにするためです。 ページから読むものは別の記録です。behavior が欄に打ったものを持ち、人が読み、検索する ものです。これには代償があります。ノードの url は、URL に残すシークレットを持つ 資源のレコードを名指さなくなります。短い値は無関係の文字も置き換えます: 値が pro なら、語 probe は ***be になります。

The storage member

browserhive:capture は、取り込んだ origin が保持していた web storage を記録する storage という member を 持たなければならない（MUST）。この member が記録するのは、その storage の 存在と形です。保存されていた値を 含んではならない（MUST NOT）。

禁じているのはこの member であって、パッケージではありません。値そのものは 別のエントリ storage/origins.jsonl に入り、値を求められた取り込みの パッケージがそれを運びます。 を参照。 分けているのは、web storage が bearer token や session 識別子を日常的に持ち、 それらが WARC の payload のどこにも現れないからです —— 既定で記録すれば、パッケージはそれを行く先々へ運ぶことになります。 どちらをパッケージが持っているかは valuesRecorded が述べます。

web storage を記録するのは、後から復元できないからです。ネットワークを一度も 渡らないため、どの WARC レコードもこれを保持していません —— localStorage から描画するページは、アーカイブが持っていない データから描画しています。この member が無いと、読み手はそうしたページと 「本当に見せるものが無かったページ」を区別できません。 completeness は助けになりません —— あれが報告するのはパッケージが保持していない body であり、 storage は一度も body になっていないからです。

          "origin": "https://www.example.co.jp",

        { "origin": "https://ads.example.net", "unreadable": true }

    }

Members

storage は profile、stage、 valuesRecorded、origins を 持たなければならない（MUST）。

  • profile —— この member が従う規則。本仕様のこの版では値は "browserhive:storage/2" でなければならない（MUST）。 記録する内容や digest の計算方法を変えた producer は、この値を 変えなければならない（MUST）。
  • stage —— 取り込みのどの時点で storage を読んだか。この版では値は "after-behaviors" でなければならない（MUST）。 stage が規範なのは、内容が変わるからです —— ページは動作しながら storage に書き込むので、behavior が走る前に読んだものと 後に読んだものは、別の状態を表します。
  • valuesRecorded —— このパッケージが、下で定義するディレクトリに 保存されていた値も併せて運んでいるかどうか。これは「値を求められた」ことを 述べるのであって、「すべての origin の値が在る」ことではありません —— valuesOversize と印の付いた origin の値は在りません。 を参照。
  • origins —— 取り込みが観測できた origin ごとに 1 つの項目を持つ配列。

Origin entries

各項目は origin を持たなければならない（MUST） —— 値は [[WACZ]] の enclosing document と同じ直列化形式、すなわち scheme・host、 および既定でない場合の port です。

web storage は origin ごとに区切られており、ページは日常的に自分以外の origin の 文書を埋め込みます —— 広告、計測のフレーム、埋め込みのプレイヤー。それらは それぞれ自分の storage を持ち、ページ自身の origin からは見えません。 したがってこれは「そのページの storage」の記録ではありません —— 取り込みが観測できた origin ごとに 1 項目であり、 第三者の origin の項目が在ることは異常ではなく想定どおりです。

そもそも storage を持てない origin —— about:blank の文書や data: URL のような opaque origin —— は記録するものが無いので 現れません。

各項目は、local と session の両方を持つか、あるいは unreadable という単一の member を値 true で持つかの いずれかでなければならない（MUST）。後者は「その origin の storage を 取り込みが読めなかった」という意味です。これは storage が空だった origin —— "keys": 0 の area として書かれる —— とは別です。 同じ形で記録すると、この member が取り除こうとしている曖昧さが戻ってきます。

ここの項目と storage/origins.jsonl の行は、1 つの記録の 2 つの半分です。項目はその origin の storage が どう見えたかを述べ —— 鍵がいくつ、何バイト、digest は何 —— 常に在ります。行は何が入っていたかを述べ、値を求められたときにだけ 在ります。どちらをパッケージが持っているかは valuesRecorded が 述べます。値を求められてもなお行を持たない origin は 2 通りあります —— 行に入れるものが無かった（unreadable として記録）か、 行に入れるものが大きすぎた（valuesOversize として記録）か。 その 2 つを区別するのが項目で、だからこそ項目のほうが常に書かれます。

local と session はそれぞれ以下を 持たなければならない（MUST）。

  • keys —— その area が保持していた鍵の数。
  • bytes —— その area の合計の大きさ。すべての鍵と値の UTF-8 表現で数えます。browser 自身の quota 会計が使う UTF-16 コード単位ではありません。
  • digest —— "sha256:" に続けて、その area の SHA-256 を 小文字の 16 進で。計算は、鍵をコードポイント順に並べ、各要素が key U+0000 value U+0000 を UTF-8 で寄与する形で行います。 並べ方と区切りは規範です —— これを決めないと同じ内容が別の digest になり、 取り込みをまたいで比較するという digest の目的が失われます。

digest を値へのコミットメントとして扱ってはならない（MUST NOT）。 値はしばしばエントロピーが低く —— フラグ、テーマ名、時刻 —— そのような digest は推測で容易に逆算できます。

項目は valuesOversize を値 true で 持ってもよい（MAY）。これは「この origin の保存値は 大きすぎたため運ばれなかった」こと、したがって「この項目がその origin について パッケージが持つすべてである」ことを述べます。 unreadable と並べてはならず（MUST NOT） —— 読めなかった storage には、超えるべき大きさがありません —— valuesRecorded が false のときにも 置いてはならない（MUST NOT）。そこではどの origin の値も もともと運ばれる予定が無く、この member は誰も下していない判断を 報告することになります。

valuesOversize を持つ項目は、それでも local と session を持たなければならない（MUST）。 ここが unreadable との違いで、意図的なものです —— 取り込みはこの origin を読めています。鍵がいくつあり、 どれだけ大きかったかを知っています。その数字が member の隣に在れば、 読み手は「値が欠けていること」と「どれだけ欠けているか」の両方を知り、 上限を上げて撮り直すかどうかを判断できます。area を落として項目を書くのは、 すでに手元にある計測を捨てることです。 

{
  "origin": "https://heavy.example",
  "local": { "keys": 1, "bytes": 2129905, "digest": "sha256:1aeb74b512b17f6fc43ade8575d452df142ade5d1515a4afcaf05dd199688c38" },
  "session": { "keys": 0, "bytes": 0, "digest": "sha256:e3b0c44298fc1c149afbf4c8996fb92427ae41e4649b934ca495991b7852b855" },
  "valuesOversize": true
}

The storage directory

[[WACZ]] は、archive・indexes・pages を避け、 datapackage.json の resources に列挙する限り、追加の ファイルやディレクトリを認めています。適合するパッケージは、その許可を 使ってもよい（MAY）。

適合するパッケージは storage/origins.jsonl というエントリを 持ってもよい（MAY）。存在する場合、他のファイルと同様に resources で宣言しなければならず（MUST）、 JSON Lines でなければならない（MUST） —— 1 行 1 つの JSON オブジェクトで、各オブジェクトは 1 つの origin が保持していた web storage を 記録します。

このエントリが存在する場合、valuesRecorded は true でなければならない（MUST）。存在しない場合、 valuesRecorded は false でなければならない（MUST）。 したがって読み手は、アーカイブ本体を開かずに、そのパッケージが保存されていた値を 運んでいるかどうかを判別できます。

隠すシークレットを持つパッケージは、このエントリを持っては ならない（MUST NOT）。したがってその valuesRecorded は false です（ を参照）。 

{
  "profile": "browserhive:storage/2",
  "origin": "https://www.example.co.jp",
  "takenAt": "2026-09-06T01:22:14.881Z",
  "stage": "after-behaviors",
  "areas": {
    "local": { "feed.cache": "[{\"id\":1}]", "ui.theme": "dark" },
    "session": { "nav.scroll": "820" }
  }
}

各行は profile、origin、[[RFC3339]] のタイムスタンプと しての takenAt、stage、areas を 持たなければならない（MUST）。areas は local と session を 持たなければならない（MUST） —— それぞれ、area が保持していたとおりに鍵を値へ写像するオブジェクトです。 storage で unreadable または valuesOversize として記録された origin は、 ここに行を持ってはならない（MUST NOT）。 したがってエントリは 1 行も持たないことがありえます（MAY） —— 値を求められたが、どの origin の値も運べなかった場合です。これは エントリが不在であること（＝そもそも値を求められなかった）とは 別の主張です。

The accessibility directory

[[WACZ]] は、archive・indexes・pages を 避け、datapackage.json の resources に列挙する限り、 追加のファイルやディレクトリを認めています。適合するパッケージは、その許可を 使ってもよい（MAY）。

適合するパッケージは accessibility/axtree.jsonl というエントリを 持ってもよい（MAY）。存在する場合、他のファイルと同様に resources で宣言しなければならず（MUST）、 JSON Lines でなければなりません （MUST）—— 1 行 1 つの JSON オブジェクトで、各 オブジェクトは、取り込んだページに対して browser が計算したアクセシビリティ ツリーのスナップショット 1 枚を記録します。

document が withheld を持つパッケージは、このエントリを含んでは なりません（MUST NOT）。この木は描画されたページから読むので、 方針がその文書の本文を archive に入れなかったときも、文書の文字を運んでしまいます。

この木を記録するのは、後から作り直せないからです。DOM とレイアウト ツリーの両方から作られ、対応する DOM ノードを持たないノード（CSS の 生成内容、リストの記号）を含み、aria-owns がノードの親を付け替える ため、その形は文書の木とは異なります。将来の browser で archive を再生しても、 別の木ができます。tls を参照ではなく記録している理由と同じです。

Snapshot members

各行は profile・url・takenAt・ stage・tree を含まなければなりません （MUST）。

  • profile —— その行が従う刈り込み規則。本仕様のこの版では、値は "browserhive:axtree/1" でなければなりません （MUST）。刈り込み規則を変える producer は、この値も 変えなければなりません（MUST）—— 読み手が、何が 捨てられたのかを言えるようにするためです。
  • url —— そのスナップショットを読んだ文書の URL。document の url と等しくなければなりません（MUST）。
  • takenAt —— 撮った時刻。[[RFC3339]] のタイムスタンプ。
  • stage —— 取り込みのどの時点で撮ったか。この版では値は "after-behaviors" でなければなりません （MUST）。時点が規範的なのは、木が変わる からです。 autoscroll は lazy load を発火させるので、behavior の 前に撮った木と後に撮った木は、別のページを記述しています。

Node shape

すべてのノードは role を持たなければなりません （MUST）。ノードは role・ name・level・url・checked・ expanded・disabled・required・ value・children 以外の member を持ってはなりません （MUST NOT）。

このうち 2 つは、他より重い意味を持ちます:

  • level —— 見出しの深さ。これが無いと heading の ノードを互いに区別できず、この木が記録するために在る文書構造そのものが 失われます。
  • url —— 画像やリンクが指す先。ノードと archive/ に 記録されたレスポンスを結ぶのはこれで、「ここに図があった」から「その図の バイト列」へ辿れるようになります。

値が無い・空・false の member は書いてはなりません （MUST NOT）。全ノードに既定値を書くと、それが囲んでいる 中身より嵩が大きくなります。

Pruning

browser が ignored と印を付けたノードは tree に現れてはなりません （MUST NOT）。その子は残し、最も近い残されたノードの 下に付けなければなりません（MUST）。

これが、隠されたテキストを記録に持ち込まないための仕掛けです。 aria-hidden や display: none で外された部分木は ignored なノードなので、そもそもこのファイルに届きません。したがって読み手は、 この木を「見えていたもの」の記述として扱えます —— WARC の 本文だけからは支えられない、より強い主張です。

role が generic・none・InlineTextBox の ノードも tree に現れてはならず（MUST NOT）、 その子は同じように残さなければなりません（MUST）。 これらの role はそれ自体では意味を持たず、残すと木の深さが倍になるだけで、 読み手が使えるものは何も増えません。

viewport の外にあることを理由にノードを落としてはなりません （MUST NOT）。エージェントにとっては妥当な判断です —— 見えないものは操作できないので。しかし、誰もスクロールしなかった部分を捨てた アーカイブは、そのページの記録ではありません。

The behaviors directory

[[WACZ]] は、archive・indexes・pages を 避け、datapackage.json の resources に列挙する限り、 追加のファイルやディレクトリを認めています。適合するパッケージは、その許可を 使ってもよい（MAY）。

適合するパッケージは、取り込みが保存の前にページ上で走らせたコードを運ぶ behaviors の下のエントリを持ってもよい（MAY）。 存在する場合、各エントリは他のファイルと同様に resources で 宣言しなければなりません（MUST）。

コードを記録するのは、後から取り戻せないからです。producer が同梱するコードは 少なくとも build が固定していますが、リクエストが運んできたコードは リクエストと共に来て、応答を捨てた時点で失われます —— しかも、それが走った名前は 提供した側が決めたものなので、同じ名前で中身の違うコードが走った 2 回は 他の手段では区別が付きません。tls を参照ではなく記録している理由と 同じです。

Runtime

適合するパッケージは behaviors/runtime.js というエントリを 持ってもよい（MAY）。存在する場合、それは producer が ページの中で評価したソースを、バイト単位でそのまま 持たなければなりません（MUST）。

producer がそのようなソースを評価したときは在らなければならず （MUST）、そうでなければ在ってはなりません（MUST NOT）。 したがってその存在は「ページ上でコードが走った」ことを述べます —— その後どの behavior が何かをしたかどうかとは無関係に。

そのソースを評価した後、producer はソースが定めた関数を、引数を付けて 呼んでもよい（MAY）。その呼び出しと引数はソースの一部ではなく、 このエントリには記録されません。引数のうち、変数は settings.variables に、 シークレットの名前は settings.secrets に在ります。シークレットの値は、 引数としてはどこにも記録されず、producer はそれをソースに書いては なりません（MUST NOT）。behavior の手に渡った後の値がどうなるかは が述べます。

これが、producer の作るどの取り込みでも runtime を同じバイト列に保ちます。値をソースに 書き込む producer は、取り込みごとに違う runtime.js を記録することになり —— シークレットも一緒に記録してしまいます。

要求しているのは「バイト単位でそのまま」であって、読みやすさではありません。 runtime を minify する producer は minify された形を記録します —— それがページの受け取ったものだからです。人が読める形が要る読み手には build があり、それがパッケージを作ったソフトウェアを名指しします。

条件は「置いたか」であって「走ったか」ではありません —— runtime と同じ条件です。ページに置かれた コードは、そのあと何を決めたにせよ、そこで走っています。作用したコードだけを 記録するアーカイブは、実行されたコードを取りこぼします。

各行は 1 つの要求を記録します: browser が始めた要求か、producer が送らせなかった要求です。 producer は要求が始まったときに行を作り、応答・終わり・失敗が届くたびに埋めていきます。 そのため、producer が記録を止めたときに終わっていなかった要求も、"pending" と して trace に入ります。リダイレクトする応答は、[[BROWSERHIVE-WARC-PROFILE]] で交信を 終わらせるのと同じく、その行を終わらせ、続く要求は別の行を始めます。同じ id を 持つ行は hop の昇順に並ばなければならず（MUST）、 そのうちの 2 行が同じ hop を持ってはなりません （MUST NOT）。

行は producer が作った順に並ばなければなりません（MUST）。 これは時刻の順ではありません: startedAt も ms も、前の行の値以上で あることを求めません。エントリは、producer が記録を止めるまでに、始まりが producer に 届いたすべての要求と、producer が送らせなかったすべての要求の行を、下に述べるとおり 残さない行を除いて、持たなければなりません（MUST）。

要求の始まりは、2 つの道のどちらかで producer に届きます。取り込んだページの側で始まった 要求は browser が伝え、その時刻は browser の時計です。producer が送らせなかった要求は、 producer 自身の決定から trace に入り、その時刻は producer の時計です。BrowserHive が作る行は この 2 種類で、送らせなかった要求は、取り込んだページのどこで出されたものでも —— 別サイトの フレームや worker の中のものも —— 行になります。行を何かの時刻で並べ替えると、誰もその順では 見ていない出来事のあいだに、順番を主張することになります。順番が要る読み手は、自分で ms で並べ、そうしたことを知ったうえで読みます。

producer は、通信の記録を止めた後、パッケージを組む前に、trace を 1 度だけ閉じます。 取り込んだページがその後に出した要求は入らず、producer がまだ埋めていた行は、その時点の ままになります: その outcome は "pending" です。

record は、在るときは archive/ の中の response レコード —— その行が記録する交信のもの —— を名指さなければなりません （MUST）。そうした行の startedAt は、そのレコードの WARC-Date と 1 文字ずつ同じでなければなりません（MUST）。2 つの行が同じ record を持ってはなりません（MUST NOT）。交信の response レコードがパッケージに無い行は、record を持っては なりません（MUST NOT）: outcome が "finished" で record の無い行は、browser が終わりまで読んだが、 producer がレコードを書かなかった応答です —— たとえば、producer が本文を受け取る前に 取り込みが止まったとき。trace の dropped が 0 のとき、archive/ の中のどの response レコードも、いずれかの行の record に名指されてい なければなりません（MUST）。

行は 3 つの時計を読んでいて、それらを混ぜてはいけません。startedAt は browser の 壁時計です —— outcome が "denied" の行だけは producer の時計で、 browser はその要求を始めていません。browser の壁時計は WARC-Date を読むのと 同じ時計で、だから行とレコードを並べて読めます。ただし壁時計は取り込みの間に合わせ直されることがあるので、2 つの行の startedAt の差は時間の長さではありません。durationMs と timing は browser の単調な時計の差で、こちらは跳びません。ms は 行を、ログの行と同じ軸の上に置きます。producer は行ごとに自分の時計を読むとは限りません: BrowserHive は最初の要求で 1 度だけ読み、その後は browser の単調な時計で過ぎた分を足します。

durationMs は、browser が伝えた要求の始まりから終わりまでです。そのため、 producer が要求や応答を調べるために止めていた時間 —— URL を方針に照らす間や、本文を 読む間 —— を含み、timing の各区間も含むことがあります。ここでの長さは、同じ 交信が、誰も記録していない browser で掛かる長さより長いことがあります。

outcome が "not-archived" か "denied" の行は、 initiator・response・timing・ durationMs・encodedBytes・record を持っては なりません（MUST NOT）。

要求者が要求を伏せるのは、パッケージがその交信を残さないようにするためです。行が、応答の status や大きさや、掛かった時間を運んだなら、trace は、残さないはずだったものを読める 2 つ目の場所になり、WARC については守られた方針が、パッケージについては守られないことに なります。そこで行は、 withheld request のレコード が述べること —— 取り込んだページがその URL を、どの method で、どの種類の資源として 求めたか、producer がどう決めたか —— と、それがいつだったかのほかは、何も運びません。 それでも、行の並びは、応答について 1 つのことを示します。no-archive の項目に 当たった要求への応答がリダイレクトで、続く要求をどの方針も伏せないとき、続く要求は、同じ id と次の hop を持つ自分の行を持ちます。そのため読み手は、伏せた 要求がリダイレクトされたことと、その行き先の URL を読み取れます。続く交信は、パッケージが 残すと決めたものなので、そのレコードはどのみち WARC に在ります。

outcome が "failed" の行は error を持た なければならず（MUST）、ほかの行は持っては なりません（MUST NOT）。endUnobservable は、 outcome が "pending" でない行に在っては なりません（MUST NOT）。durationMs は、 outcome が "finished"・"redirected"・ "failed" のどれでもない行に在ってはなりません （MUST NOT）。encodedBytes は、outcome が "finished" でない行に在ってはなりません （MUST NOT）。urlCut・ endUnobservable・fromCache は、在るときは値が true で なければなりません（MUST）。

producer は、取り込んだページが要求を出しうるすべての場所を聞いているわけではなく、要求の 終わりが、聞いていない場所に伝えられることがあります: 別サイトのフレームの文書は、 取り込んだページの側で始まり、フレームの側で終わります。endUnobservable を持つ "pending" の行は、そうした要求です。その行が述べるのは、producer が終わりを 見ることができなかったことであって、終わりが無かったことではありません。

producer は、行を自分の決めた大きさに収めるために url を 切ってもよい（MAY）。url を切った行は urlCut を持たなければなりません（MUST）。 data: の URL は中身を URL そのものに持ち、その中身は、パッケージが残さない はずだった本文や、取り込んだページの文字でありえます。url も、 initiator の url も、data: の URL のデータを持っては なりません（MUST NOT）: producer はそうした URL を、media type を 終えるコンマより先までは書かず、その URL が行の url のとき、行は urlCut を持たなければなりません（MUST）。データの 代わりに何を書くかは producer が決めます。BrowserHive は URL の長さを書きます。

producer は、trace を自分の決めた上限に収めるために、行を残さ なくてもよい（MAY）。そうする producer は、何行を残さなかったかを trace の dropped で述べなければなりません （MUST）。エントリの中には、それらがどこに在ったかの印はありません。BrowserHive は、 はじめに作った行と最後に作った行を残し、その間の行を残しません: 取り込みが時間切れに なったときに読み手が要るのは、最後の行だからです。

random/recorder.js は、producer が値を記録するためにページの中で評価した ソースを、バイト単位でそのまま持たなければなりません （MUST）。behavior にとっての behaviors/runtime.js と同じです （ を参照）。

このプロファイルは、エントリを ZIP ファイルの中にどう収めるかについて何も求めません。 パッケージのほかの文字のエントリと同じく、そこで圧縮してもよい（MAY）。

recorder は、取り込んだページのスクリプトと、それが受け取る値の間に立ちます。値を、あるいは producer が値を変えなかったという主張を吟味する読み手には、記録をしたコードが要り、そのコードは、 書き留めなければ取り込みが終わると失われます。resources で宣言したエントリは、 パッケージの digest に覆われ、署名があれば署名にも覆われます。

読みやすさのために複数行で示しています。ファイルの中では、各オブジェクトはちょうど 1 行を占めます。

どの行も、profile と kind を持つ JSON オブジェクトで なければなりません（MUST）。profile は行が従う決まりで、 本仕様のこの版では値は "browserhive:random/1" で なければなりません（MUST）。kind は行が述べるもので、 "document" か "draw" でなければなりません （MUST）。

kind が "document" の行（文書の行）は、producer が 記録した文書 1 つを述べます。その行は document・url・ frame・dpr を持たなければなりません（MUST）。

Member型必須意味
documentnumberはい その文書の値の行が文書を名指す番号。0 以上の整数。
urlstringはい browser が確定させた、その文書の URL。シークレットの値は置き換えてあります （下を参照）。
framestringはい 取り込みの主フレームの文書なら "main"、フレームの中の文書なら "frame"。
dprnumberはい その文書を読み込んだ読み込みの device pixel ratio。settings の devicePixelRatios の要素のどれか。
recordstringいいえ その文書を運んだ HTTP か HTTPS の交信の response レコードの WARC-Record-ID の URI。その欄が付ける山括弧は付けません。
datestringいいえ そのレコードの WARC-Date。

2 つの文書の行が同じ document を持ってはなりません （MUST NOT）。文書の行は document の昇順で並ば なければなりません（MUST）。frame は "main" か "frame" でなければなりません （MUST）。文書を運んだ HTTP か HTTPS の交信の response レコードをパッケージが 持つとき、行は、archive/ の中のそのレコードを名指さ なければならない（MUST）record と、そのレコードの WARC-Date と 1 文字ずつ同じでなければならない（MUST） date を持たなければなりません（MUST）。そうでなければ、 行はそのどちらも持ってはなりません（MUST NOT）。

kind が "draw" の行（値の行）は、取り込んだページの スクリプトが受け取った値 1 つを述べます。その行は document・seq・ api・caller を持たなければならず（MUST）、 value を持ってもよい（MAY）。api が "crypto.getRandomValues" の値の行は bytes も持た なければならず（MUST）、ほかの値の行は持っては なりません（MUST NOT）。

Member型必須意味
documentnumberはい スクリプトが呼び出しをした文書の、文書の行の document。
seqnumberはい その行が、同じ文書の値の行の中で何番目か: 最初が 0 で、続く行ごとに 1 つ増えます。 0 以上の整数。
apistringはい スクリプトが呼んだ関数: "Math.random"・ "crypto.getRandomValues"・"crypto.randomUUID"。
callerstringはい 呼び出しをしたスクリプトの URL。browser が call stack で伝えたとおりで、 シークレットの値は置き換えてあります（下を参照）。stack がそうした URL を名指さない ときは空の文字列。
bytesnumberapi が "crypto.getRandomValues" のとき スクリプトが渡した typed array の byteLength。0 以上の整数。
valuenumber か stringいいえ スクリプトが受け取った値（下を参照）。

値の行の document は、エントリの中でそれより前に在る文書の行の document と等しくなければなりません（MUST）。 seq は、文書の最初の値の行で 0 でなければならず（MUST）、 ほかのどの値の行でも、同じ文書のその前の値の行より 1 つ多くなければなりません （MUST）。1 つの文書の中では、値の行は recorder が呼び出しを見た順に 並ばなければなりません（MUST）。別々の文書の行は混ざって 並んでもよい（MAY）: ある文書の行が、別の文書の 2 つの行の間に 在ることがあります。

api は "Math.random"・"crypto.getRandomValues"・ "crypto.randomUUID" のどれかでなければなりません （MUST）。caller は、呼び出しをしたスクリプトの、browser が call stack で伝えた URL でなければなりません（MUST）: recorder 自身の frame を数えずに、 stack の中で HTTP か HTTPS の URL を持ついちばん内側の frame —— 呼び出しにいちばん近い frame —— のものです。そうした frame が無いとき、caller は空の文字列で なければなりません（MUST）。

value は、在るときは、スクリプトが受け取った値を変えずに、次のように書いたもので なければなりません（MUST）:

  • "Math.random" では、0 以上 1 未満の number。
  • "crypto.randomUUID" では string: 正準形の UUID。小文字の 16 進数字 32 個を、 8・4・4・4・12 個の組に分けてハイフンでつないだもの。
  • "crypto.getRandomValues" では string: スクリプトが渡した typed array の、 呼び出しが埋めたとおりのバイト列を、ちょうど bytes 個、 RFC 4648 の 4 節の base64 で、 標準のアルファベットと padding を使って符号にしたもの。

producer は、取り込んだページのスクリプトが受け取る値を変えては なりません（MUST NOT）。producer は、値を残さないと決めたとき、 値の行から value を除いてもよい（MAY）。たとえば、 シークレットを渡された取り込みでの crypto の関数の値や、自分の決めた上限より長い crypto.getRandomValues の配列のバイト列です。そのとき行は、呼び出しがあったことと、 どのスクリプトがしたかと、文書の呼び出しの中で何番目かを、なお記録します。value の無い行は、残さなかった行ではなく、truncated はそれについて何も述べません。

producer は、エントリを自分の決めた上限に収めるために、値の行を残さなかったり、記録を 止めたりしてもよい（MAY）。このプロファイルは、その上限の数を 定めません。そうする producer は、random の truncated を true にしなければなりません（MUST）。エントリの中には、 どこで行を残さなかったかの印はありません。

文書の行の url と値の行の caller は、隠すシークレットの値の出現も、 残すシークレットのそのままの値も、長さに関わらず持ってはなりません （MUST NOT）（ を参照）。producer は、 が挙げる URL と同じように置き換えるので、 WARC-Target-URI が URI のままであるように、書いたものは URL のままです: 読み手は、caller を、アーカイブしたレコードの URL の中から引けます。

trace と同じく、行は WARC のレコードとは別に読まれ、行に残した値は、行の行く先のどこへでも 付いて行きます。これには代償があります。URL が残すシークレットを持っていたスクリプトの caller は、そのスクリプトのレコードの WARC-Target-URI と同じでは なく、そうした文書の url も、その record が名指すレコードのものと 同じではありません。送られたとおりの URL は、そのレコードに在ります。

行は取り込んだページから来ます。recorder はページのスクリプトの間で走り、スクリプトが 受け取ったものと、呼び出しをした stack を producer に渡します。そのため行は document のページ由来の記録に入ります: 文書を伏せたパッケージは行を 1 つも持たず、 random がそれを述べます。

Reading this entry

読み手は random/recorder.js を実行してはなりません （MUST NOT）。behaviors や preload と同じく、producer が走らせたものの 記録であって、アーカイブされたページの一部ではありません。

文書を replay する読み手は、記録した値をページのスクリプトに返し てもよい（MAY）。そうする読み手は、文書の行 D が述べる、replay した 文書の中で、URL が S のスクリプトが関数 A を呼んだ n 回目（1 から数える）の呼び出しに、 caller が S で api が A の、D の n 番目の値の行の value を返すべきです（SHOULD）。そうした行が無いとき、 行が value を持たないとき、あるいは値が呼び出しに合わないとき —— たとえば bytes と別の長さの配列での crypto.getRandomValues の 呼び出し —— 読み手は、自分の値を記録した値として示してはなりません （MUST NOT）。

replay した文書をどの文書の行が述べるかは、読み手が決めます。そのために行が差し出すのは、 url・frame・dpr と、在るときは record と date です。2 度以上読み込んだページは、読み込みごとに文書の行を持ちます。 random の truncated が true のときは、残さなかった行が その後の行をずらし、n 番目の行が n 回目の呼び出しを記録しているとは限りません。

読み手は、caller を producer の申告として読んでは なりません（MUST NOT）。browser が伝えるのは、call stack に 見つけたスクリプトで、その URL は、取り込んだページがそのスクリプトに与えたものです。 取り込んだページは、自分のスクリプトに好きな名前を付けられます。producer は browser が 述べたことを取り次ぐだけで、言葉を選んだのは取り込んだページです。

パッケージの digest が覆い、署名があれば署名が覆うのは、パッケージの中の行です。ほかの どこかで見せたり伝えたりする同じ行は、その写しで、写しをパッケージに結び付けるものは 何もありません。行を頼りにする読み手は、パッケージから読みます。

これは、読み手がパッケージから取り込んだページのスクリプトへ何かを渡すことを認める、本仕様で 最初の節です。behaviors と preload の節は、パッケージが持つコードを読み手が走らせることを 禁じ、この節も recorder を走らせることを禁じます。この節が認めるのはもっと狭いもので、 値です —— ページ自身のスクリプトが乱数を求めたところに、読み手がそうでなければ自分で作る値の 代わりに返すもの。そうする replay は、取り込みが選んだものを選び、そうしない replay も、 選び直しながら、パッケージをなお replay します。

Constraints inherited from replay

この節の要求は [[WACZ]] に由来しません。既存の WACZ 読み手が実際に行っていることに由来し、 これらを無視したパッケージは、基底の仕様を満たしていても実務上は読めません。

  • datapackage.json の profile member は "data-package" でなければならない。読み手はこの値で 分岐し、知らない値を拒むため、本プロファイルを識別する用途には使えません。 を参照。
  • datapackage.json の config と metadata を、本仕様が 定める値を運ぶために使ってはならない。読み手がこれらに意味を 割り当てています。
  • CDXJ 索引の値は、数値に見えるものも含めて string で なければならない。
  • CDXJ 索引は非圧縮で、.gz で終わらないパスに格納され なければならない。読み手は拡張子で位置を特定し、 展開を行いません。
  • CDXJ の行の filename field は archive/ からの相対で なければならない。読み手はディレクトリを自分で前置するので、 それを含む行は archive/archive/… に解決され、何も見つかりません。 を参照。

ここに記すのは、パッケージの作成者がこれらを満たせるようにするためです。それぞれが なぜ存在するかは実装史の問題であり、本仕様の外で文書化されています。同じ種類の制約が もう 1 つありますが、それはパッケージではなく WARC のレコードに掛かるもの —— response のペイロードの形 —— で、[[BROWSERHIVE-WARC-PROFILE]] に書いてあります。

Security and privacy considerations

tls は来歴の証明ではありません。証明書は公開情報で、誰でも取得して複製を提示できます。 これらのフィールドを持っていることは、誰が要求に応答したかについて何も言いません。保存する 価値があるのはもっと狭い 2 つです —— issuer は接続が傍受されたときに変わり、 有効期間は取り込みが主張する時刻と突き合わせられます。そしてどちらも、書き留めなければ 取り込みの後には残りません。

completeness が主張するのは不在であって、正しさではありません。このパッケージが 実証的に保持していない本文を報告します。保持している本文がオリジンの配信したものである、 とは主張しません。complete も、隠すシークレットの値を持つので落とした本文が無い、 とは言いません。それを言うのは、truncated が secret の body not kept のレコードです。

適合するパッケージが、保持している本文について主張するのは [[BROWSERHIVE-WARC-PROFILE]] の Payloads の節の 内容です —— それは wire を渡ったバイト列なので、payload digest はオリジンが送ったものの digest であり、producer が符号を変えた写しのものではありません。例外は、 BrowserHive-Redacted の欄が payload を挙げる redacted のレコードです。 その本文では値を置き換えてあり、digest が保証するのはレコードが持つバイト列だけです。 どちらも、オリジンが URL の名指す相手だったことは言いません。tls を参照してください。

パッケージは completeness に URL を、tls に host 名を、trace に、取り込みが 始まりを見た各要求の URL を記録します。方針が伏せた要求と、応答の届かなかった要求の URL も含みます。取り込んだ ページが URL に個人データを載せていた場合、それらの URL はアーカイブとともに旅をします。

アクセシビリティツリーは、browser が要素に対して計算した名前を運びます。それは ページの可視テキストから作られます。文書の本文が WARC の本文に入っているなら、 そのテキストはそこに既に入っています。しかも刈り込み規則によって、 露出は本文より狭くなります: ignored なノードを除くので、aria-hidden や display: none で隠されたテキストは、レスポンス本文には在っても、この木には 現れません。方針が文書の本文を archive に入れなかったなら、そのテキストは本文に 入っていないので、パッケージは、木も、ページの文字と題も、その文書から 読んだ写しも、スクリーンショットも、ページがログに書いた行も持ちません（document を参照）。

写しは、そのときのページの姿 —— 文字と、パスワードの欄を除く欄の値 —— を持ちます （[[BROWSERHIVE-WARC-PROFILE]]）。木と違ってページより狭くはなく、ページが隠した文字も 入ります。settings のシークレットの値は写しの中で、少なくともそのままの形と HTML の escape の形で置き換えられ、隠すシークレットの値は、出現の取りうるすべての綴りで置き換えられます。 それ以外にページが変換したシークレットや、誰もシークレットと告げなかった値は残ります。

この決まりは文書の単位で働きます。描画されたページには、副資源を通って届いた中身 —— スクリプトが出した要求への応答や、frame の文書 —— が入りえます。方針がそうした本文の どれかを archive に入れなくても、残された文書のページ由来の記録からは、その中身は 締め出されません。その中身を完全に締め出したい要求者は、文書ごと締め出す必要があります。 例外はスクリーンショットだけで、それも要求の種類によります（下を参照）。

スクリーンショットは、viewport が見せていたものを運びます: 取り込んだページの文字、画像、 再生中だった動画の 1 こま、フレームの文書（別サイトのフレームを含む）、そして、そのページと behavior が欄に入れたもの。画像なので、その中の何かを探すことも、置き換えることも できません。取り込みがシークレットを渡されたとき、メディア型の方針を持っていたとき、 urlPolicies の no-archive か no-body の項目が、browser が 文書・画像・メディアの要求と伝えた要求に当たったとき、文書が 伏せられたときに、パッケージが —— 何かを取り除いたスクリーンショットではなく —— スクリーンショットを 1 枚も持たないのは、そのためです（screenshots を参照）。

この条件は、画像が写しうるものの全部には届きません。誰もシークレットと告げなかった値は、 取り込んだページが見せていれば、画像に写ります。urlPolicies の no-archive か no-body の項目が当たった要求のうち、producer が読んだ どの報告でも、browser が文書とも画像ともメディアとも伝えなかった要求への応答から、 そのページが描いたものも写ります: スクリプトが取ってきてそのページに書き込んだ文字、スタイルシートが与えた見た目、フォントの 字形。決めるのは、browser がその要求を何と呼んだかです。スクリプトが自分で取ってきて自分で 描く画像は、browser にとってはスクリプトの要求です。スクリプトが小分けに取ってきて player に 渡す動画や音声も同じです: browser はそれらの要求をスクリプトの要求と伝えるので、 それらに当たる URL の方針は、スクリーンショットを外しません。メディア型の方針は 別で、その方針が 1 つでも在れば、スクリーンショットは外れます。producer に見えない要求にも、 この決まりは届きません。そうした中身も画像に入れたくない要求者は、文書ごと締め出すか、 スクリーンショットを撮らない producer に取り込ませる必要があります。

この条件は、画像が写すものより先にも届きます。方針が伏せる画像を 1 つでも読み込む ページ —— 分析の host を伏せる方針の下の、誰にも見えない計測用の画像など —— は、どの 取り込みでもスクリーンショットを持ちません。producer は本文を残さないので、見えていた画像と 見えていなかった画像を区別できないからです。そうした方針が当たって、リダイレクトされた だけの要求 —— 取り込んだページに見せるものを何も運ばなかった要求 —— も数えます。producer は 要求の時点で決めるからです。メディア型の方針は、応答がその方針に当たったかどうかに関わらず、 その下で撮ったどの取り込みからもスクリーンショットを外します。そして、画像を撮った後に 出された要求に当たった方針も、その画像を外します。producer には、どの画像がどの応答を 写しているかが分からないからです。

パッケージを読む道具に確かめられるのは、パッケージが持つ印です: secrets、contentTypePolicies、document と snapshots の withheld、withheld request のレコード、そして trace の行と 突き合わせた body not kept のレコード。これらの印は、producer を縛る決まりの全部では ありません。producer がレコードを書かなかった要求 —— 別サイトのフレームの中で出された要求や、 応答が届かなかった要求 —— は道具に見えず、画像を撮ることが取り込んだページを変えたか どうかも見えません。パッケージだけを 持つ者には、ピクセルが browser の見せたものであることも確かめられません: パッケージの digest と、在るなら署名は、画像のバイト列を覆いますが、それがどう作られたかは何も言いません。

ログは、ページが書いた文字を運びます。source が "page" の行は、 取り込んだページのスクリプトが console に書いたものと、それらが捕まえなかった誤りを持ち、 そこには URL・識別子・ページ自身の文字が日常的に入ります。文書が伏せられたとき、ログは それらを 1 行も持ちません（ を参照）。この要求が見るのは document が名指す文書だけで、行はどの文書が書いたかを名乗らないので、ページが 伏せられた文書から残された文書へ移ったときは、はじめの文書の行が残ってしまいます。そこで producer は、snapshots がある時点を "withheld" と記録したときは いつでも、ページの行を全部省いてよく、省いた producer はそれを自分の行で述べます。読み手は、 ページの行が書かれなかったのではなく省かれたことを見分けられます。

ログの中で producer がシークレットの値を置き換えるのは、値がそのままの形で現れたところ です —— msg にも data にも、鍵にも値にも、どの深さでも、長さに 関わらず。隠すシークレットの値は、出現の取りうるすべての綴りで置き換えます。シークレットを ほかの形 —— ハッシュにしたものや、分けたもの —— で書く behavior は、 その形をパッケージに入れ、誰もシークレットと告げなかった値も残ります。そして behavior が 行を書く通り道はページの main world に在るので、ページのスクリプトは behavior のもののように 読める行を書けます（ を参照）。

trace は、取り込んだページがどの URL を求めたか、その中の何がそれを求めたか、各交信に どれだけ掛かったかを述べます。方針が伏せた要求については、行は、WARC と同じもの —— URL・method・資源の種類 —— を運び、応答の status・大きさ・掛かった時間は運びません （ を参照）。それでも、応答について、行の並びから読めることが 1 つ在ります: no-archive の項目に当たった要求がリダイレクトされ、その先の URL を どの方針も伏せないとき、次の行は同じ id と次の hop を持つので、 読み手は、伏せた要求がリダイレクトされたことと、その行き先を知ります。行き先の交信は、 パッケージが残すと決めたものなので、どのみち WARC に在ります。行の中で producer は、シークレットの値を、残すものも 隠すものも、URL と失敗の文に現れたところで置き換えます。ほかの形にした値は残り、誰も シークレットと告げなかった値も残ります。data: の URL は、データを除いて 書きます。initiator が名指すものは、取り込んだページが自分について述べたこと であって、producer の申告ではありません。そして、パッケージの digest と署名が覆うのは パッケージの中の行だけです: ほかのどこかに出る同じ行は、写しです （ を参照）。

取り込みが記録を求められたとき、random/values.jsonl は、取り込んだページの スクリプトが Math.random・crypto.getRandomValues・ crypto.randomUUID から受け取った値を運びます。ページがそうした値を引くのは、 何を見せるかを決めるためでもあり、安全のためでもあります: セッションや端末の識別子、nonce、 ページの中で作る鍵。producer はその使い道を見分けられず、パッケージを持つ者は誰でも、 残した値を全部読めます。そのため、シークレットを渡された producer は、crypto の 関数の値を残すのを避けるべきです。value の無い行も、呼び出しは記録します （ を参照）。recorder は、ページのスクリプトがこれらの関数を呼ぶ ところに立つので、記録するのはそのスクリプトが recorder に見せたものであり、行の caller は、取り込んだページが自分のスクリプトに付けた名前です （ を参照）。ログと同じく、document の決まりが見るのは document が名指す文書です: ページが伏せられた文書から残された文書へ移ったときは、 はじめの文書の行が残ります。

storage は、パッケージが既に保持している以上のものを晒しません。 記録するのは鍵の数・バイト数・digest です。値は記録せず、digest は値では ありません —— ただし上に書いたとおり、エントロピーの低い内容に対する digest は 隠し場所にもなりません。

storage/origins.jsonl を併せて持つパッケージは、 より多くを晒します。web storage は bearer token、 セッション識別子、未送信の下書きを日常的に保持しており、そのどれも WARC の payload には現れません。この profile の中で、取り込みがネットワークから 一度も受け取っていない資料を適合パッケージが運びうる場所は、ここだけです。 producer は既定でこのディレクトリを出力しないべきである（SHOULD）。 読み手は valuesRecorded によって、アーカイブ本体を開かずに どちらであるかを判別できます。

シークレットの値を置き換えて締め出せるのはパッケージからであって、ページから ではありません。behavior はページの main world に在る runtime から値を読み、そこではページ 自身のスクリプトも同じ値を読めます。別の実行 context を使わない限り、producer はそこで値を 隠せません。値をネットワークへ送る behavior —— URL・ヘッダ・本文のどれであれ —— は、 パッケージが何を記録するかに関わらず、値をオリジンに渡します。

隠すシークレットを隠せるのは、producer が値を認識できるところだけです。 [[BROWSERHIVE-WARC-PROFILE]] の Security の節が挙げるものは、パッケージにも残ります: 値から作られたもの（ハッシュ、暗号文、オリジンが本文で発行した token など）、出現でない綴り、 そして値がそこにあったという事実で、これは *** がどこであれ示します。 storage の area の digest は、何かを置き換える前の area の中身から作るので、ページが保存した 値の候補を読み手に試させることがあります。シークレットの跡をアーカイブから完全に締め出したい 要求者は、それを送らない behavior を渡す必要があります。

パッケージが出現を持たないことは、パッケージだけを持つ読み手には確かめられません。パッケージが 値を持たないからです。パッケージを読む道具に確かめられるのは、producer がしたと述べることの 形だけです。確かめられるのは値を持つ producer で、パッケージを書く前に全部のファイルを探せます。

secretArchive を埋めるのは要求の側で、それが何を旅させるかを決めます。 残すシークレットの値は、WARC のレコードと、そこから取った URL の中で読めるままで、 パッケージを人に渡す者はそれも渡します。

対照的に variables は、意図して値のまま記録します。個人データを変数に入れた 要求者は、それをアーカイブに入れたことになります。2 つの線を引くのは要求の側です —— このプロファイルは、秘密だと告げられたものと、そうでないものを、告げられたとおりに 記録します。

browser は記録を行った build を名指しし、これは必須です。origin へ別の身元を 提示する producer — たとえば User-Agent を差し替えた場合 — でも、 この member は変わりません。サーバへ送るものと、パッケージが報告するものは別です。 build の版を秘匿したい運用者は、適合するパッケージがそれを開示することを知っておく 必要があります。
