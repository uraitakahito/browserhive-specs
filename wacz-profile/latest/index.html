This specification profiles [[WACZ]]. It constrains how a WACZ package is written and defines the additional members BrowserHive records inside it, so that a reader holding only the archive can tell what the capture obtained, what it did not, and under what settings it ran.

This is a working draft. It describes what BrowserHive writes today. It has no standing beyond that project and is not endorsed by the publishers of [[WACZ]].

This version names the WARC files of a package data-NNN.browserhive.warc.gz instead of data-NNN.warc.gz, and it has them conform to BrowserHive WARC Profile 1.4.0 (see ). A package written against 1.24.0 names its WARC files the old way, and they name WARC Profile 1.3.0, so it does not conform to 1.25.0. This version also recommends that a package be named ….browserhive.wacz (see ), and says that a reader does not infer conformance from a name. This is intended, and it is why conformsTo names a version: a reader holding an older package can still tell what it was written against. Earlier versions — 1.0.0, 1.1.0, 1.2.0, 1.3.0, 1.4.0, 1.5.0, 1.6.0, 1.7.0, 1.8.0, 1.9.0, 1.10.0, 1.11.0, 1.12.0, 1.13.0, 1.14.0, 1.15.0, 1.16.0, 1.17.0, 1.18.0, 1.19.0, 1.20.0, 1.21.0, 1.22.0, 1.23.0 and 1.24.0 — remain published at their own URLs for that reason, but BrowserHive no longer produces them.

A capture has to decide when a page is ready to be taken, and every way of deciding is a bet: a fixed pause robs a page that was ready and cuts short one that was not, and a signal-based wait can reach its deadline first. Before version 1.7.0 a package could not say which of these happened. That matters to a reader weighing the package as evidence, because the difference between “the page looked like this” and “the page looked like this while it was still loading” is recoverable from nothing else in the package: the records say what arrived, not what was still on its way when the capture moved on.

Introduction

A [[WACZ]] package says what was captured. It does not say what was missed, nor under what conditions the capture ran. Those facts are knowable only at capture time, and they are lost once the capturing process exits.

That loss matters because the archive is the thing that travels. A reader opening a package three years later has no access to the API response, to the machine that produced it, or to the logs that machine kept. If the package cannot answer “is anything missing here?”, nothing else can.

This profile therefore requires a package to carry its own account of the capture: which bodies are absent and why, which limits were in force, which requests it declined to send and which it sent but did not keep, what it removed from the page before recording it, which secrets it was given and which of them it kept, which certificates the origins presented, the log the capture wrote as it ran, the requests it saw begin, with how each one ended, and whether it kept pictures of the page, with the reason when it kept none. None of these change what [[WACZ]] means. They record what would otherwise be unrecoverable.

Conformance

The conformance target of this specification is a package: a single file. Conformance is a property of files, not of the software that writes them. An implementation may write conforming and non-conforming packages at different times, and this specification says nothing about which.

A conforming package is a conforming [[WACZ]] package. This specification adds requirements. It removes none, and it relaxes none.

A package that conforms to a version of this specification is called a BrowserHive WACZ. Every BrowserHive WACZ is a WACZ package. This specification sets no requirement on what any other WACZ package holds.

Where this specification uses the terms MUST, MUST NOT, SHOULD and MAY, they are to be interpreted as described in [[RFC2119]].

JSON member names are case-sensitive. Where a member is described as holding a timestamp, its value MUST be an [[RFC3339]] date-time in UTC.

The browserhive:capture member

The datapackage.json of a conforming package MUST contain a member named browserhive:capture whose value is a JSON object.

This member MUST NOT be nested inside config or metadata. Those names carry meaning for [[WACZ]] readers; see .

Members of browserhive:capture not defined here MAY be present. Readers MUST ignore members they do not recognise.

Conformance declaration

browserhive:capture MUST contain a member conformsTo whose value is the URL of the version of this specification the package claims to satisfy. 

"browserhive:capture": {
  "conformsTo": "https://uraitakahito.github.io/browserhive-specs/wacz-profile/1.25.0/"
}

The declaration is carried here rather than in the profile member of datapackage.json, which is not available for this purpose.

A reader MUST NOT infer conformance from the mere presence of browserhive:capture, nor from the name of the package or of the files in it (see and ). Without conformsTo, the version a package was written against is unknown.

build

browserhive:capture MUST contain a member build identifying, in machine-readable form, the software that produced the package.

MemberTypeRequiredDescription
versionstringyesRelease identifier.
revisionstringyesSource revision the build was made from.
buildTimestringyesWhen the software was built.
 
"build": {
  "version": "3.4.0",
  "revision": "0776cae",
  "buildTime": "2026-08-21T04:04:09.000Z"
}

The format of version is not constrained. A build made from a release carries something like "3.4.0", while a build made between releases may carry a value that includes its distance from the last one, such as "3.4.0-12-gabc1234". Both say which build produced the package. A reader should treat the value as an identifier — equal values mean the same build — rather than parse it as a version number.

[[WACZ]] already defines software. That member is prose, and no two producers write it alike, so nothing parses it. build exists so the same facts can be read by machine without guessing at a format.

browser

browserhive:capture MUST contain a member browser describing the browser that performed the capture. It MUST contain a member product whose value is a string. 

"browser": {
  "product": "Chrome/151.0.7922.137"
}

The spelling is not defined here. The value is whatever the browser names itself as, so a package produced by a different engine carries a different shape. A reader can compare two values for equality; it cannot assume a grammar.

The value MUST NOT be a placeholder. A producer that cannot obtain it MUST NOT produce a conforming package: an archive whose recording browser is unknown is outside this profile, and omitting the member is not a way to say so.

settings

browserhive:capture MUST contain a member settings recording the settings that were in force for this capture.

Values MUST be the resolved values, not the values a request asked for. A request that says nothing still runs under some setting, and it is that setting the archive has to report.

MemberTypeRequiredDescription
signaturestringyes Either "required" or "none": whether this capture was permitted to be published unsigned.
viewportobjectyes Members width and height, both integers, in CSS pixels.
devicePixelRatiosarray of numberyes The device pixel ratios the page was loaded at, in the order it was loaded. The number of entries is the number of loads.
sessionstringyes Whether the capture ran in a browser context created for it and discarded afterwards, or in one the capturing process reuses across captures. It tells a reader whether the package could depend on state left by an earlier capture.
userAgentstringyes The User-Agent the capture sent, after resolving what the request asked for. Without a request for one, the browser's own value.
behaviorsarray of objectyes Behaviors that ran after load, in the order they ran. Each entry carries id, the name the behavior was run under, and origin, one of "builtin", "site" or "custom". A producer that holds no behaviors of its own writes "custom" for every entry. See the behaviors directory.
preloadarray of objectyes Scripts that were supplied to run before navigation, in the order they were registered — not the ones that reported something, because these cannot report at all. Each entry carries id, the name the script was supplied under. An empty array states that none were supplied. See the preload directory.
variablesobjectyes The values the request supplied for the behaviors to read, by name. Each value is a string. An empty object states that none were supplied. See .
secretsarray of stringyes The names of the values the request supplied in confidence for the behaviors to read, in lexicographic order. Names only — this member holds no value (see below). An empty array states that none were supplied.
secretArchiveobjectyes Which of those secrets the request asked to keep in the records of the WARC. Each member's name is an entry of secrets and its value is the string "keep". A secret not named here is hidden. An empty object states that none were kept. See .
limitsobjectyes The caps that were in force for this capture. Members maxResponseBytes and maxTaskBytes, the body caps, and maxWarcBytes, the size at which a new WARC file is started (see ). All three integers, in bytes.
urlPoliciesarray of objectyes What the capture did about each URL pattern that was in force, in the order the patterns were evaluated. See urlPolicies.
contentTypePoliciesarray of objectyes What the capture did about each media type that was in force. See contentTypePolicies.
acceptLanguagestringno Present only when the capture set one, since it changes what origins return.
 
"settings": {
  "signature": "none",
  "viewport": { "width": 1280, "height": 800 },
  "devicePixelRatios": [1],
  "session": "isolated",
  "userAgent": "Mozilla/5.0 (X11; Linux x86_64) AppleWebKit/537.36 (KHTML, like Gecko) HeadlessChrome/151.0.0.0 Safari/537.36",
  "behaviors": [
    { "id": "autoscroll", "origin": "builtin" },
    { "id": "autofetch", "origin": "builtin" }
  ],
  "preload": [],
  "variables": {},
  "secrets": [],
  "secretArchive": {},
  "limits": {
    "maxResponseBytes": 20971520,
    "maxTaskBytes": 209715200,
    "maxWarcBytes": 1000000000
  },
  "urlPolicies": [
    { "pattern": "*://*.example-analytics.com/*", "action": "deny" }
  ],
  "contentTypePolicies": []
}

In this example session records that the capture ran in a context of its own, and the single entry in devicePixelRatios that it loaded the page once. The two entries under behaviors are the behaviors that ran — not the ones that were enabled. userAgent is the browser's own value because the request asked for none. acceptLanguage is absent because this capture set none, and variables, secrets and secretArchive are empty because the request supplied no values for the behaviors. The values themselves are the producer's to choose; this profile does not define the spellings shown here.

The exception is origin. A behavior's id is a name its supplier chose and this specification says nothing about how it is spelled, but origin answers a question about the package rather than about the behavior — whether the code came from the producer or from the request — so its three values are defined here.

devicePixelRatios is a list rather than a number because a capture may load the page more than once. Recording a single value would tell a reader that one rendering is absent when it is present.

The values MUST appear in the order the page was loaded, so that a reader can say not only which renderings the archive holds but which one was drawn last — artefacts that carry the page's appearance follow the state left by the final load.

A capture that loads the page twice carries one value per load. A request that asked for a User-Agent shows the value that was sent, one that set acceptLanguage shows it here as well, and one that supplied values for its behaviors shows them — the variables with their values, the secrets by name alone, and in secretArchive the ones it asked to keep: 

"settings": {
  "signature": "required",
  "viewport": { "width": 1280, "height": 800 },
  "devicePixelRatios": [1, 2],
  "session": "isolated",
  "userAgent": "Mozilla/5.0 (X11; Linux x86_64) AppleWebKit/537.36 (KHTML, like Gecko) Chrome/151.0.0.0 Safari/537.36 BrowserHive",
  "behaviors": [
    { "id": "autoscroll", "origin": "builtin" },
    { "id": "example.com:gallery", "origin": "custom" }
  ],
  "preload": [],
  "variables": { "query": "gallery" },
  "secrets": ["api_token", "member_id"],
  "secretArchive": { "member_id": "keep" },
  "acceptLanguage": "ja,en;q=0.9",
  "limits": {
    "maxResponseBytes": 20971520,
    "maxTaskBytes": 209715200,
    "maxWarcBytes": 1000000000
  },
  "urlPolicies": [],
  "contentTypePolicies": [{ "prefix": "video/", "action": "no-body" }]
}

The two measure different things. maxResponseBytes applies to the body of a single response; maxTaskBytes applies to the running total of the bodies written into this package. A snapshot or a screenshot is weighed against the same line: one that would take the bytes the capture keeps past it is left out (see snapshots and screenshots).

The difference matters to a reader. maxResponseBytes weighs one response at a time, so any number of responses under it are kept and the size of the package cannot be inferred from it. maxTaskBytes watches the accumulated total, so once the line is crossed bodies are dropped regardless of size — a small response among the dropped ones is not a contradiction.

maxWarcBytes is not a body cap. No body is dropped at it: it is the size at which the producer closes the current WARC file and starts the next (see ). It is recorded here so that a reader can check the files in archive/ against the line that produced them.

limits MUST be present even when no body was dropped. It is the only place the archive can say which line a truncated body crossed — a record of a body not kept carries the fact and the actual size, but whether that size was too much is only legible next to the line.

The truncatedUrls member of completeness does not distinguish which of the two a body crossed, even though the remedies differ (one response too large versus the whole page too heavy). A reader who needs the distinction has to look outside the package, at what the capture reported.

userAgent is the value that was sent, not the text the request asked for: a request may leave part of the value for the producer to fill in, and what an origin saw is the filled-in value. Every request record whose WARC-Target-URI is mainPageURL MUST carry this value in its User-Agent header.

Only those records are bound. A page's own scripts may send another value on the requests they make, and the requests of a service worker may not be in the package at all. browser keeps naming the browser that performed the capture whatever this value says, so a reader can tell what the origins were told from what actually captured.

variables and secrets record what the request handed to the behaviors to read (see ), and secretArchive which of the secrets it asked to keep. All three MUST be present even when the request supplied nothing, so that an empty object and an empty array are claims rather than omissions.

variables carries the values. A behavior that searches for a term ran under some term, and a reader weighing the package has to be able to say which; the code alone cannot, because the same code runs under every value.

secrets carries names only. The names are recorded so that a reader can tell the behaviors read something this member does not hold. The producer MUST NOT write the value of a secret into secrets or secretArchive. What the rest of the package holds of the values is set out in , and what a behavior then does with a value in .

A secret the request says nothing about is hidden, so secretArchive lists only what the request asked to keep. Each name in secretArchive MUST be an entry of secrets, and each value MUST be the string "keep".

As with a behavior's id, the names under variables, secrets and secretArchive are chosen by whoever supplied the values, and this profile says nothing about how they are spelled. The order of secrets is defined here — lexicographic — so that two packages that read the same names list them the same way.

completeness

browserhive:capture MUST contain a member completeness, the package's own account of what it does not hold: the bodies it is missing, and the targets that crashed.

MemberTypeRequiredDescription
bodylessUrlsarray of stringyes URLs that appeared only as 304. The body never crossed the wire, so the archive cannot hold it.
truncatedUrlsarray of stringyes URLs whose body the capture dropped on reaching a size limit.
uninterceptedUrlsarray of stringyes URLs whose body crossed the wire but the producer could not obtain as bytes, so the archive holds none (see Response payloads in [[BROWSERHIVE-WARC-PROFILE]]).
crashedTargetsarray of objectyes Targets other than the main document whose renderer crashed during the capture (see ).
completebooleanyes true if and only if all four arrays are empty.
 
"completeness": {
  "bodylessUrls": [],
  "truncatedUrls": [],
  "uninterceptedUrls": [],
  "crashedTargets": [],
  "complete": true
}

A capture that lost nothing takes this shape. complete is derived from the four arrays, so four empty arrays alongside false never occur.

A capture missing bodies for all three reasons: 

"completeness": {
  "bodylessUrls": [
    "https://example.com/assets/app.css"
  ],
  "truncatedUrls": [
    "https://example.com/media/hero.mp4",
    "https://example.com/media/poster.png"
  ],
  "uninterceptedUrls": [
    "https://example.com/api/feed"
  ],
  "crashedTargets": [],
  "complete": false
}

Here the stylesheet appeared only as a 304: its body never crossed the wire, so the archive cannot hold it. The video and its poster were dropped at a limit. The feed's body arrived, but the producer could not read it as bytes. A URL dropped twice still appears once.

The three arrays of URLs MUST be sorted by code point, so that two captures of the same page produce comparable output.

The three are separate members because they call for different responses. A 304 is the origin's doing and cannot be recovered from here; a body dropped at a limit is this side's doing and returns if the limit is raised; a body that was not intercepted is the producer's failure, and no setting of the request brings it back.

Responses that legitimately carry no body MUST NOT be listed: redirects, 204, bodies omitted by a policy the requester configured — a no-body entry of urlPolicies, or an entry of contentTypePolicies — and bodies dropped for holding the value of a hidden secret, which the requester chose by not keeping the secret (see ). Reporting those would tell the reader only what they had already decided.

This holds whatever the size of the omitted body. A body a policy omitted is one the capture never set out to fetch, so it cannot have been dropped at a limit: it MUST NOT be listed in truncatedUrls even when it is larger than maxResponseBytes, or arrives after the total has reached maxTaskBytes. Listing it there would tell the reader that raising a limit recovers a body the requester asked not to keep.

The WARC describes the same bodies one record at a time: each response recorded without the body the server sent carries a record of a body not kept ([[BROWSERHIVE-WARC-PROFILE]]), whose truncated says why. The URLs of bodies dropped at a size limit — too-large and task-cap — are listed in truncatedUrls, and those of bodies that were not intercepted — not-intercepted — in uninterceptedUrls. Bodies a policy omitted — url-policy and content-type — and bodies dropped for a hidden secret — secret — are listed in neither.

[[BROWSERHIVE-WARC-PROFILE]] defines those values by the producer's limits and policies without naming them. In a package, they are the ones recorded in settings:

truncatedThe limit or policy, in settings
too-large The body was larger than limits.maxResponseBytes.
task-cap The body would have taken the bodies written into the package past limits.maxTaskBytes.
url-policy The first entry of urlPolicies to match the URL has the action no-body.
content-type An entry of contentTypePolicies matches the media type.
not-intercepted No setting. The body crossed the wire, but the producer could not obtain it as bytes.
secret No limit and no policy. The body was not a text body and held the value of a hidden secret: a name in secrets that secretArchive does not name, or a value treated as one (see ).

crashedTargets

A page can run in more than one renderer process: a cross-site iframe has a process of its own. When such a renderer crashes, the rest of the page goes on and the capture can finish, but what that target was showing is gone. A screenshot shows the gray box Chromium draws for a crashed frame, but that is a picture no tool reading the archive can act on, and a saved document still holds the ordinary iframe element, so the package has to say so.

crashedTargets MUST contain one entry for each target, other than the main document, whose renderer crashed after the capture started and before the package was assembled.

MemberTypeRequiredDescription
typestringyes The kind of target, in the browser's own word: iframe, service_worker and so on.
urlstringno The target's URL. See below for when it is absent.
statusstringyes How the renderer ended, in the browser's own word: killed when something outside the process ended it, crashed when the process itself failed, and so on.
 
"completeness": {
  "bodylessUrls": [],
  "truncatedUrls": [],
  "uninterceptedUrls": [],
  "crashedTargets": [
    {
      "type": "iframe",
      "url": "https://ads.example.net/slot/1",
      "status": "killed"
    }
  ],
  "complete": false
}

url MUST be omitted when the first entry of urlPolicies to match it has the action no-archive or deny, and when document has withheld. A target's URL comes from the page, so it MUST NOT carry out what the requester asked not to keep.

The array MUST be sorted by url, then type, then status, each by code point, with an entry without a url ahead of those with one.

The main document does not appear here. When its renderer crashes before the package is assembled, the capture fails and no package is written. After that the renderer is no longer needed, so the crash changes nothing the package says. A same-site iframe and a dedicated worker run in the main document's renderer, so their crash is the main document's.

coverage

browserhive:capture MAY contain a member coverage describing how far down the page the capture reached.

MemberTypeRequiredDescription
scrollExhaustedbooleanyes true when scrolling stopped at a step limit rather than at the end of the page — that is, when material below was never requested.
scrollStepsnumberyesSteps actually taken.
scrolledPxnumberyes Approximate depth reached: steps multiplied by viewport height.
 
"coverage": {
  "scrollExhausted": true,
  "scrollSteps": 40,
  "scrolledPx": 32000
}

The three values are read together. scrolledPx is scrollSteps multiplied by the viewport height recorded in settings — 40 × 800 here — so a reader can check one against the other. And because scrollExhausted is true, the 32,000 pixels are where the capture stopped, not where the page ended: whatever lay below was never requested, and therefore leaves no trace anywhere else in the package.

coverage MUST be absent when no scrolling behavior reported. It MUST NOT be written with default values: scrollExhausted: false asserts that the page was covered, and a capture that never scrolled has not earned that claim.

settle

browserhive:capture MUST contain a member settle stating how the wait after navigation ended: on the page settling, or on a deadline with the page still changing.

MemberTypeRequiredDescription
strategystringyes Which signals were watched, in what order. This version defines "fully-loaded": load, then a pause of limits.minMs, then network, cpu and dom together.
endedBystringyes "quiet" when every watched signal was satisfied before the deadline; "deadline" otherwise.
waitedMsnumberyes Milliseconds from the navigation returning to the wait ending.
devicePixelRationumberyes Which load this observation is of; one of the entries of devicePixelRatios. When there are several, the last.
limitsobjectyes The bounds in force, as numbers: minMs, maxMs (the deadline), quietMs (the window every quiet signal is held to) and networkConcurrency (requests still counted as quiet).
loadobjectyes atMs: when the document was seen fully loaded.
networkobjectyes quietAtMs: when no more than limits.networkConcurrency requests had stayed in flight for limits.quietMs.
cpuobjectyes quietAtMs: when no long task — a task holding the main thread for 50 ms or more — had run for limits.quietMs.
domobjectyes quietAtMs: when no element had been added or removed and no text rewritten for limits.quietMs. Attribute changes do not count.
 
"settle": {
  "strategy": "fully-loaded",
  "endedBy": "quiet",
  "waitedMs": 2310,
  "devicePixelRatio": 1,
  "limits": { "minMs": 1000, "maxMs": 3000, "quietMs": 1000, "networkConcurrency": 0 },
  "load": { "atMs": 210 },
  "network": { "quietAtMs": 2205 },
  "cpu": { "quietAtMs": 2104 },
  "dom": { "quietAtMs": 2004 }
}

Every time is in milliseconds from the navigation returning, on the same clock as waitedMs. Pauses a producer inserts between its own operations are not part of that clock.

A signal's time is a number when the signal was satisfied, and null when the deadline came first. The time MUST be written even when it is null. Omitting it instead would read as “this signal was not watched”, which is a different fact.

endedBy is derived from the four times. A producer MUST NOT write "quiet" while any of them is null, nor "deadline" while none is.

A page where the deadline came first: 

"settle": {
  "strategy": "fully-loaded",
  "endedBy": "deadline",
  "waitedMs": 3116,
  "devicePixelRatio": 1,
  "limits": { "minMs": 1000, "maxMs": 3000, "quietMs": 1000, "networkConcurrency": 0 },
  "load": { "atMs": 188 },
  "network": { "quietAtMs": 2011 },
  "cpu": { "quietAtMs": 2108 },
  "dom": { "quietAtMs": null }
}

Here the page kept rewriting its text — a clock, say — so the DOM never stayed still for a second, and the capture went on at the three-second deadline. The network and the CPU had settled; only the DOM had not.

endedBy: "deadline" does not mean the capture failed. The package holds what the page had become by then. It records that the page had not settled, which a reader weighing the package as evidence needs to know and cannot recover from anything else in it.

Each quiet signal asks whether the page stayed still for limits.quietMs, not whether it would have stayed still. A page that is silent for longer than the window and then changes reads as settled before the change.

dismissal

browserhive:capture MAY contain a member dismissal recording what the capture removed from the page before recording it, and what it looked for.

A capture that removes a consent banner changes the document it then archives. Nothing else in the package says so: the removed element leaves no trace in the WARC, in the index, or in the rendered snapshot, and a reader cannot tell it from a page that never carried one.

MemberTypeRequiredDescription
selectorsarray of objectyes The selectors that were in force, in the order they were evaluated. Members framework and selector, both strings.
heuristicobjectyes The thresholds that governed removal of elements no selector named. Members enabled (boolean), minViewportCoverageRatio (number) and minZIndex (number).
frameworkstring or nullno The framework of the first entry that matched, or "heuristic" when only the thresholds fired. null when nothing was removed.
removedSelectorsarray of stringno The selectors whose element was removed. A subset of selectors, in evaluation order.
unusableSelectorsarray of stringno Entries of selectors the reader of the page could not evaluate. These matched nothing because they were not valid selectors, which is not the same claim as matching nothing.
removedOverlaysnumberno Elements removed by the thresholds rather than by a selector.
devicePixelRationumberno Which load this observation is of; one of the entries of devicePixelRatios.
unreadabletrueno Present when removal was attempted but could not be carried out.
 
"dismissal": {
  "selectors": [
    { "framework": "OneTrust", "selector": "#onetrust-banner-sdk" },
    { "framework": "Cookiebot", "selector": "#CybotCookiebotDialog" }
  ],
  "heuristic": { "enabled": true, "minViewportCoverageRatio": 0.3, "minZIndex": 1000 },
  "framework": "OneTrust",
  "removedSelectors": ["#onetrust-banner-sdk"],
  "unusableSelectors": [],
  "removedOverlays": 0,
  "devicePixelRatio": 1
}

dismissal MUST be absent when no removal was attempted. Absence therefore means the page was archived as it was served; it does not mean nothing was found.

When dismissal is present, selectors and heuristic MUST be present even when nothing was removed. They are what makes the outcome checkable: an empty removedSelectors next to twenty entries says the page carried no banner any of them names, while the same empty list next to no entries says only that nothing was looked for. This is the argument that makes urlPolicies mandatory on a capture that filtered nothing.

A package MUST NOT carry unreadable alongside framework, removedSelectors, unusableSelectors or removedOverlays. A removal that could not be carried out has observed nothing, and writing an empty result beside it would assert that the page held no banner.

Scrolling also changes what the capture sees, and what it did is already recorded — by coverage, which states how far down the page it reached. A second account of the same act here would be a copy, and one of the two would eventually be the stale one.

A capture that loads the page more than once removes elements on each load; removal is not consent, so a consent framework re-renders on the next load. removedSelectors is an observation of one document at one moment, not a union across loads, and devicePixelRatio is what ties it to the load it came from.

document

browserhive:capture MUST contain a member document naming the document the page-derived records were read from, and saying whether they were withheld.

The page-derived records are the snapshots of the document (see snapshots), the screenshots of the page (see screenshots), the text and title of the entries in pages/pages.jsonl, the title of datapackage.json, accessibility/axtree.jsonl, and the lines of logs/capture.jsonl whose source is "page" (see ). They are read from the rendered page rather than from the network, so nothing in the WARC payload bounds them: a policy that keeps a document's body out of the archive does not by itself keep that document's text out.

MemberTypeRequiredDescription
urlstringyes, unless withheld is "unattributed"The URL of the document, as the browser committed it; for "deny", the URL whose request was denied. The value of a hidden secret is replaced in it (see ).
withheldstringnoWhy the page-derived records are not in the package. Absent when they are.
 
"document": {
  "url": "https://example.com/next",
  "withheld": "url-policy"
}

The document is the one in the main frame when the page-derived records were read. It need not be the one at the requested URL: a server redirect or a client-side navigation replaces the document, and the records describe whatever replaced it. url is that document's URL after any such redirect or navigation, as the browser committed it.

The page-derived records are read stage by stage. The snapshot of a stage, and the entry of pages/pages.jsonl that lists it (see ), are read from the document in the main frame at that stage, and the screenshot of a stage shows the page while that document is in its main frame. The title and text of the entry of the document in pages/pages.jsonl, the title of datapackage.json and accessibility/axtree.jsonl are read after the behaviors, from the document that document names, as is the snapshot of the "after-behaviors" stage. The lines of logs/capture.jsonl whose source is "page" are written all through the capture rather than read at a stage, and they count as read from the document that document names. The rules below on withheld apply at each stage to the document at that stage: a stage whose document they withhold has no snapshot, and snapshots records it as "withheld". Nor has it a screenshot (see screenshots).

When a deny entry keeps the main frame from navigating (see urlPolicies), no document replaces the one before: the browser shows an error page in its place, and that page is not a document of the capture. The document is then the one the navigation was headed for, and url is the URL whose request was denied.

withheld, when present, MUST be one of the following. The first four name the policy that kept the document, or its body, out of the archive (see ).

  • "url-policy" — the first entry of urlPolicies to match the document's URL has the action no-body.
  • "content-type" — no entry of urlPolicies matches the document's URL, and an entry of contentTypePolicies matches its media type.
  • "no-archive" — the first entry of urlPolicies to match the document's URL has the action no-archive, so the package holds neither the response that served the document nor its body: only the record of the withheld request, and that request's line in the trace.
  • "deny" — the first entry of urlPolicies to match the document's URL has the action deny, so the document was never requested. Page-derived records read at that point would describe the browser's error page, not the document.
  • "unattributed" — the producer cannot tell which document the records were read from, for example because the main frame navigated while they were being read.

A producer MUST set withheld to "url-policy", "content-type", "no-archive" or "deny" when, and only when, that policy applied to the document. The rule runs in both directions. A policy that matched only a redirect hop, or only a document the page navigated away from, withholds nothing; a policy that matched the document withholds its records even when the requested URL did not match it.

When withheld is present, the package MUST NOT carry the page-derived records read from that document. The title of datapackage.json MUST NOT be read from the page, and the package MUST NOT contain accessibility/axtree.jsonl. The entry of the document in pages/pages.jsonl (see ) MUST NOT have a text or title member. That entry MAY carry the reason as textWithheld; if it does, the value MUST equal withheld. A package whose document is withheld holds no screenshot of any stage either (see screenshots).

A body dropped at a size limit does not withhold the page-derived records. The limits are the capture's, not the requester's, and a page whose body did not fit in the archive is the one whose text is most useful.

screenshots

browserhive:capture MUST contain a member screenshots, an array that says, for each stage at which the capture copies the document (see snapshots), whether the package holds a screenshot of that stage, and why when it holds none. A screenshot is a picture of the page as the browser showed it at that stage, recorded in the WARC (Screenshots in [[BROWSERHIVE-WARC-PROFILE]]) as two records: a resource record that holds the picture, under a WARC-Target-URI that begins urn:browserhive:screenshot:, and a metadata record that says what the picture is. The array MUST hold an entry for "after-load" and, when the capture ran a behavior (when behaviors in settings is not empty), an entry for "after-behaviors" after it, and no other entry.

The page a screenshot shows is the page as the capture had it by then. Where the capture removed something from the page before recording it, the picture shows the page without it, and dismissal says what was removed.

Taking screenshots is the producer's choice, and this profile does not ask for them. What it asks is that a package say what became of them, and that it hold none where a picture could show what the capture was asked to keep out of the package (below).

datestringyes The WARC-Date of that record, a timestamp.
recordstringyes The URI in the WARC-Record-ID of that record, without the angle brackets that field puts around it.
bytesnumberyes The size of the picture, in bytes: the Content-Length of that record.

A screenshot shows the viewport, the part of the page the browser was showing, and nothing beyond it. The viewport of a capture is the one settings records, and the metadata record of a screenshot says how large the picture is and at which device pixel ratio the page was showing.

The entry for a stage of which the package holds none MUST carry stage and skipped, and nothing else — for instance {"stage": "after-load", "skipped": "withheld"}. skipped MUST be one of the following, and where more than one of them holds, the one that comes first in this list:

  • "disabled" — the producer was not set to take screenshots.
  • "secret" — the capture was given a secret: secrets in settings is not empty.
  • "withheld" — a policy of the capture, or what became of the document, keeps the screenshots out (below): the capture had a media type policy; a no-archive or no-body entry of urlPolicies matched a request for a document, an image or media, or a request of which the package cannot show the kind; the document is withheld at the end of the capture or at that stage; or the producer cannot tell which document the picture of that stage shows.
  • "task-budget" — keeping the picture would have taken the bytes the capture keeps past limits.maxTaskBytes (see settings), the limit the screenshots share with the bodies of responses and the snapshots.
  • "failed" — the producer tried to take the screenshot and could not, or left it untried after it had given up on an earlier one (below).

It follows that an entry carries "secret" only in a package whose secrets is not empty, and that in such a package every entry carries "disabled" or "secret".

The package MUST hold a screenshot for every entry that names one, and no screenshot that no entry names.

A picture cannot be edited as text can. A producer cannot find a value, or an image a policy withheld, in the pixels of a screenshot, and it cannot take one out and leave the rest. What a capture was asked to keep out of its package can therefore be kept out of a picture only by not keeping the picture. A package MUST NOT hold a screenshot, of any stage, when any of the following is true of it:

  1. secrets in settings is not empty. The page can show the value of a secret, in a field a behavior typed it into or in what an origin sent back. This holds for a kept secret as for a hidden one: keeping a secret keeps it in the records of what crossed the wire, and what is read from the page has it replaced all the same (see ), which a picture cannot have.
  2. contentTypePolicies in settings is not empty. A media type policy applies to a response by its media type, which is known only once the response has arrived, and the producer does not see the media type of every response the page showed: not inside a frame from another site, and not of a response that had not come when the capture ended. It cannot tell, then, that no picture shows a body such a policy was to leave out. BrowserHive has no media type policy of its own, so this holds only for a capture that was configured with one.
  3. document carries withheld. This is the rule of document for the page-derived records, taken one step further: the package holds no screenshot of an earlier stage either, as it holds no line the page wrote to the log, whichever document wrote it.
  4. A WARC file in archive/ holds a record of a withheld request whose action is no-archive, and that record either carries the resourceType Document, Image or Media, or carries no resourceType.
  5. A WARC file in archive/ holds a record of a body not kept whose truncated is url-policy, and the line of trace/events.jsonl whose record names the response record that record refers to (see ) either carries the resourceType Document, Image or Media, or carries no resourceType; or no line names that response record, as when the producer left lines out of the trace. The status of the response does not matter: where the record of a body not kept is that of a redirect, it counts as that of any other response does.

In the fourth and the fifth condition, a no-archive or no-body entry of urlPolicies matched a request for a document, an image or media. A policy applies to a request, and the producer decides at the request, before it knows what the response will be. Whether the response had a body for the page to show therefore does not enter into it, and the conditions hold for a hop of a redirect as well. This is a different line from the one document draws, where a policy that matched only a redirect hop withholds nothing: the screenshots are decided for the capture as a whole, not for one document.

Document, Image and Media are compared, character for character, with the value of resourceType in the record or in the line. They are the browser's words, which this profile does not define (see ). A producer whose browser uses other words treats the requests these three stand for — those for a document, a frame's included, for an image, and for audio or video — in the same way.

The screenshot of a stage shows the document in the main frame at that stage. A package MUST NOT hold the screenshot of a stage whose document the rules of document withhold, nor one of which the producer cannot tell which document it shows, because the document in the main frame changed while it took the picture. The entry for a stage that snapshots records as "withheld" MUST carry skipped.

Behind the fourth and the fifth condition stands a rule that binds the producer. A producer MUST NOT keep a screenshot of a capture in which the first entry of urlPolicies to match the URL of a request has the action no-archive or no-body, and the browser reported that request as Document, Image or Media in any report of it that the producer reads. A browser can describe one request in more than one place, and not in the same word: Chromium calls the request for a video's captions Media where a producer stops requests and TextTrack where it records them, and an image that an object or embed element loads Other and Image. One such report is enough. The rule holds whatever became of the request — a response recorded without its body, a redirect, a failure, a response that had not come when the capture ended — and wherever in the page it was made, inside a frame from another site, where the producer writes no record of it, included.

The two conditions and the rule do not cover the same captures. The two conditions also hold where the package cannot show of what kind the request was: where the record or the line carries no resourceType, or the producer left the line out of the trace. A producer keeps no screenshot of such a capture either, whatever the browser reported, and the entries carry "withheld". In the other direction, a tool that reads the package does not see every request the rule reaches. It cannot see a request the producer wrote no record of, such as one made inside a frame from another site, one that a no-body entry matched and that no response answered, or one whose response had no body to send, for which [[BROWSERHIVE-WARC-PROFILE]] does not ask for that record. Nor can it see that a request counted when the record names it in another word than the report that counted. The entries then carry "withheld", and nothing else in the package says why.

A deny entry does not: a request that was never sent brought the page nothing to show. Where such an entry kept the main frame from navigating, the browser's error page stands in the document's place, and document carries withheld. A body dropped at a size limit does not either, for the reason it does not withhold the other page-derived records (see document): the limits are the capture's, not the requester's. Nor does an entry of urlPolicies that applied only to requests the package shows to be of another kind, such as those for a script or a style sheet, and that no report the producer read called a document, an image or media. What that leaves in a picture is set out in .

The producer cannot tell which picture shows which response: the browser can have a response long before the page shows it. So the conditions look at the capture as a whole. A policy can also apply to a request made after a picture was taken — a page asks for an image below the viewport only when a behavior scrolls to it — so a producer has to hold its pictures until it stops recording, and write them or drop them together then. One it had already written into a WARC file could not be taken back out.

[[BROWSERHIVE-WARC-PROFILE]] has a screenshot show the page at the viewport size, the device pixel ratio and the scroll position the page had when the producer began to take it, so the producer changes none of them for the sake of the picture. In a package, that is what keeps settings true of everything the capture recorded after the picture: the page went on under the viewport and a device pixel ratio that settings lists. A tool that reads the package cannot see whether the page was changed.

A page that keeps its main thread busy can keep the browser from handing over a picture for longer than a capture can wait. A producer MAY give up on a screenshot after a time of its own, and one that has given up on a screenshot MAY leave the later ones of that capture untried. It records each of them as "failed".

A screenshot has no entry in pages/pages.jsonl: it is not a page a reader opens (see ). Its resource record is in the CDXJ index (see ), where a reader finds it by the url and the date of the entry.

A package that conforms to this version holds entries for the two stages above and no others. A later version of this profile may add entries of another kind, for screenshots that are not taken at a stage, which [[BROWSERHIVE-WARC-PROFILE]] leaves room for.

A package without a screenshot could come from a producer that takes none, from a capture whose pictures had to be left out, or from one that could not take them. The entry says which, so that a reader does not take a picture the capture was not to keep for one it failed to take, and a tool that shows the capture can say why there is no picture.

A host reached over HTTPS whose connection revealed no details MUST be recorded with the value null. Omitting the key instead would read as “this host was plain HTTP”, which is a different fact.

Host name matching uses san, not subject. subject records the common name, which current readers do not match against — the value of subject MUST NOT be read as “this is the host name it was accepted for”.

A missing chainRef MUST NOT be read as “this host presented no certificate”. Chain retrieval can fail for reasons unrelated to the host.

tls.chains

An object whose keys are the values used by chainRef and whose values are arrays of base64-encoded DER certificates. Each array MUST be ordered leaf first.

Hosts sharing a chain SHOULD share one entry. Certificates are commonly reused across the hosts of one page, and storing a copy per host inflates the package for no gain.

Chains are stored rather than referenced. Certificate Transparency holds the same bytes, but evidence that depends on a third-party service remaining reachable is weaker for that dependence — and a private CA's chain, which is the case worth examining, was never logged there at all.

Package name

[[WACZ]] requires a ZIP file that follows it to use the extension .wacz. The producer SHOULD give a BrowserHive WACZ a name that ends in .browserhive.wacz: the extension [[WACZ]] requires, after a mark that lets a person or a program holding the file tell what it is before opening it.

The mark is a hint, not a declaration. A package keeps or loses its name with every copy, and anyone can give a file any name. A package that conforms keeps conforming under another name that ends in .wacz, with or without the mark, and a name with the mark proves nothing (see ).

Archive files

[[WACZ]] requires the archive/ directory to hold one or more WARC files, with the extension .warc.gz when they are compressed with GZIP and preferably .warc when they are not, and says nothing else about their names, nor about their number or what each one holds. This section fixes the names and the number, so that a reader can tell whether a package holds every file the producer wrote, and a producer can bound the size of a single file. What each file holds is the subject of [[BROWSERHIVE-WARC-PROFILE]].

Every WARC file in archive/ MUST conform to BrowserHive WARC Profile 1.4.0, and its warcinfo record MUST name that version in conformsTo (see The warcinfo record there). That specification fixes the records: their payloads, the records in which the values of hidden secrets are replaced, the records of bodies not kept, of withheld requests and of windows not opened, the snapshots of the document and the screenshots of the page, the warcinfo record that begins each file, and that the records of one exchange, those of one snapshot and those of one screenshot share a file.

The archive/ directory MUST contain only files named data-NNN.browserhive.warc.gz, where NNN is three decimal digits, numbered contiguously from 000. A capture whose records fit in one file has exactly data-000.browserhive.warc.gz. The name ends in the extension [[WACZ]] requires, after the mark browserhive, so that a WARC file taken out of its package can still be told for a BrowserHive WARC file by its name; as with the package (see ), the mark is a hint, not a declaration.

Each WARC file in archive/ MUST be compressed with GZIP, as [[WACZ]] has a file named .warc.gz be.

The name a file gives itself in the WARC-Filename of its warcinfo record MUST be its name in archive/, without the directory: data-000.browserhive.warc.gz, not archive/data-000.browserhive.warc.gz.

The producer MUST start a new file before writing an exchange when the current file is at or above maxWarcBytes bytes (see settings). Consequently every file except the last MUST be at least maxWarcBytes bytes long, and a file MAY exceed it by at most one exchange.

The filename field of each CDXJ line MUST name the file relative to archive/ (data-001.browserhive.warc.gz, not archive/data-001.browserhive.warc.gz); readers prepend the directory themselves.

The metadata records that [[BROWSERHIVE-WARC-PROFILE]] defines — records of bodies not kept, of withheld requests and of windows not opened — are not required to appear in the package's CDXJ index. A reader looking for them reads the WARC.

The resource record of each snapshot, and that of each screenshot (see screenshots), MUST appear in the CDXJ index: a reader that serves archived pages finds a snapshot through it, and a reader that shows a screenshot finds the picture without reading the WARC files through. The searchable key of its line MUST be the record's WARC-Target-URI as it is — a urn:browserhive:snapshot: or urn:browserhive:screenshot: URI, which has no SURT form — and its JSON MUST NOT carry status, because no server answered with one. The metadata record of a snapshot or of a screenshot, like the records above, is not required to appear. 

archive/data-000.browserhive.warc.gz    warcinfo (WARC-Filename: data-000.browserhive.warc.gz), exchanges …
archive/data-001.browserhive.warc.gz    warcinfo (WARC-Filename: data-001.browserhive.warc.gz), exchanges …
indexes/index.cdxj                      … {"filename":"data-001.browserhive.warc.gz","offset":"153","length":"2048",…}

A capture that follows links records for as long as the crawl runs, and a single file that grows with it cannot be read in part, verified in part, or kept safe in part once the process dies. Bounding the file keeps every closed file whole and lets a reader seek into the package by index without reading what precedes. The bound is the producer's setting rather than a constant of this profile because the right size depends on where the package will be stored and read; the convention elsewhere is one gigabyte.

Pages

[[WACZ]] lists the pages of a package in pages/pages.jsonl, and a reader that serves archived pages opens a page by the url and ts of its entry. This section fixes the entries, so that the document the capture was asked for, and each snapshot of it (see snapshots), opens as a page.

The first entry of pages/pages.jsonl MUST be the entry of the document. After it, the file MUST have one entry for each snapshot, in the order of snapshots, and no other entry. The entry of the document:

  • url MUST be the URL the capture was asked for, written as the URL serializer of the URL Standard writes it, without its fragment. That is the URL of the first request the capture made for the document: a URL with an empty path gains its trailing slash, as the request did. A producer refuses a request whose URL holds the value of a hidden secret, and the value of a kept secret stays in it (see ).
  • ts is the time the capture started.
  • The entry MUST NOT carry stage.
  • id MUST differ from that of every other entry.
  • title and text, when present, are read after the behaviors, from the document that document names.

The entry of a snapshot:

  • url and ts MUST be the WARC-Target-URI and the WARC-Date of the snapshot's resource record.
  • stage MUST be the stage of the snapshot.
  • id MUST differ from that of every other entry. Readers keep one of the entries that share an id and drop the rest.
  • title and text, when present, are read from the document at that stage (see document).

The mainPageURL of datapackage.json MUST be the url of the first entry of pages/pages.jsonl, the entry of the document.

A snapshot is a copy of the document's DOM without the page's scripts, so what the scripts show — a picture put in place once an animation ends, a list that a request fills in — can be missing from it. The entry of the document opens the archived responses with the page's scripts running, as the page was first shown. When the document was archived, the URL the capture was asked for names a record: the response that served the document, or the redirect that led to it, which a reader follows.

Readers differ in where they start. One may open mainPageURL; another may list the entries newest first, which puts the document last. A link that wants a reader to show the document names its url and ts.

URL and media type policies

A capture may treat some requests differently from the rest: it may decline to send them, decline to record them, or record them without their bodies. browserhive:capture.settings MUST record what it did, so that a reader can tell which of those happened without access to the capture's configuration.

A policy acts on network bodies. What it does to the records read from the rendered page — the page's text, its title and its accessibility tree — is set out under document, and what it does to the screenshots of the page under screenshots.

urlPolicies

urlPolicies is an ordered array. Each entry is an object with two members:

MemberTypeRequiredDescription
patternstringyes The pattern that was in force, spelled exactly as the capture was configured with it.
actionstringyes One of the values below.

A pattern is matched against the whole URL of a request. The character * matches any sequence of characters, including none; every other character, ? included, matches only itself; and the comparison is case-sensitive. A pattern therefore has to allow for a query string: *://example.com/a.js does not match https://example.com/a.js?v=2.

A capture matches a pattern against the URL before any value of a secret is replaced in it (see ). In a package that names a secret, a URL holding *** can therefore match a different entry from the one the capture applied, or none. A reader MUST NOT take the result of matching such a URL for what the capture did.

actionRequest sentWhat the package holds
denyno A record of the request in the WARC, and a line of the trace (see ). Nothing left the capturing machine for that URL, so no origin learned of the capture through it.
no-archiveyes A record of the request in the WARC, and a line of the trace. The capture let the request go; the package keeps nothing else of the exchange.
no-bodyyes The request and response records, without the response body.

The record a deny or no-archive entry leaves is a record of a withheld request ([[BROWSERHIVE-WARC-PROFILE]]). Its action is the entry's action, and its pattern MUST be the entry's pattern, spelled exactly as it appears here, so that a reader can find the entry. A no-body entry leaves no such record: the exchange is recorded as usual, and its absent body is described by a record of a body not kept whose truncated is url-policy — never as a body dropped at a size limit (see completeness).

A deny entry applies to every request the capture causes, whichever part of the page makes it: the main frame's navigations, including those that follow a server redirect and those a script starts; frames, including frames from other sites; and dedicated and service workers. A producer that lets one of these requests leave the capturing machine has not honoured the entry. A page opens no window during a capture (see ), so no window is left for an entry to reach.

A capture whose first navigation a deny entry matches MUST NOT produce a package. Nothing was loaded, so the settle report would describe a wait that never ran. A capture that loaded the page and was then denied a navigation MAY produce one; its document carries withheld: "deny".

The handshake of a WebSocket cannot be held back the way other requests can. A capture that opened a WebSocket whose URL a deny entry matches MUST NOT produce a package: the request was sent, and a package would claim otherwise.

The array MUST be present even when it is empty, and an empty array MUST mean that no policy was in force. Without that rule a reader cannot separate a page that requested nothing unusual from a capture that declined to record what it requested, and those are different claims about the same package.

The order is the order in which the capture evaluated the patterns, and a capture MUST apply the first entry whose pattern matches. Recording the order is what lets a reader answer “which policy applied to this URL?” when more than one pattern would match it. 

"urlPolicies": [
  { "pattern": "*://cdn.example.com/tracker.js", "action": "deny" },
  { "pattern": "*://cdn.example.com/*",          "action": "no-body" }
]

In this example a request for tracker.js is never sent, while everything else on the same host is fetched and recorded without its body. Reversing the two entries would change what the capture did: the broader pattern would match first, and the tracker would be fetched.

contentTypePolicies

contentTypePolicies is an array whose entries carry a prefix (matched against the response's media type) and an action. no-body is the only action this version defines: a media type is known only once the response has arrived, so deny cannot apply.

The array MUST be present even when it is empty, for the same reason as urlPolicies. A package in which it is not empty holds no screenshot (see screenshots). 

"contentTypePolicies": [
  { "prefix": "video/", "action": "no-body" }
]

Windows the page asks for

A capture records one page. While it runs, a producer MUST NOT let the page be given a new top-level browsing context — a window or a tab — whoever asks for one: the page's own script, a frame inside it, or a script the capture request supplied. The page is answered as a browser answers a popup it blocked: window.open returns null, and a link or form that targets a new window opens nothing.

Each time the page asked for one is recorded in the WARC as a record of a window not opened ([[BROWSERHIVE-WARC-PROFILE]]). No request was sent for the window's document, so the record is written whether or not an entry of urlPolicies matches the URL, and it is not a record of a withheld request.

A capture in which a window opened nonetheless MUST NOT produce a package. The window's requests would have reached their origins without appearing in the package, and the package would describe the capture as one that opened nothing.

A browser opens a window only for a page that holds user activation, the trace of a person's click or keystroke. BrowserHive never gives the page one: the code it evaluates on the page, including the behaviors and preload scripts a request carries, runs without it. That is what refuses the window, and it is also why those scripts cannot use an API that needs a gesture, such as window.open, the Fullscreen API or writing to the clipboard.

Values of secrets

A request may supply values in confidence for the behaviors to read, and settings records their names. A behavior can send such a value over the network and a page can show it, so the capture meets it in what it records. The Redacted records section of [[BROWSERHIVE-WARC-PROFILE]] defines the terms secret, hidden secret, occurrence, redacted record and text body, and says what a single WARC file does about them. This section says which secrets of a package are hidden, and what the rest of the package does about them.

Each name in secrets names a secret. One that secretArchive names is a kept secret, and any other is a hidden secret.

The rules of this section replace a value where it stands as text or as bytes. A screenshot (see screenshots) is a picture: it can show a value the page showed, and nothing in its bytes is an occurrence that a producer could find and replace. A package whose secrets is not empty therefore holds no screenshot, whether its secrets are hidden or kept.

Requests a producer refuses

Some requests cannot be carried out without breaking the rules of this section. A producer MUST refuse the following requests, and MUST NOT produce a package for them:

  • A request that gives a hidden secret a value shorter than eight characters. Replacing so short a value reaches text that has nothing to do with it. The request can ask to keep the value instead.
  • A request to capture a URL that holds an occurrence of the value of a hidden secret. The first entry of pages/pages.jsonl and mainPageURL are that URL (see ), and a reader opens the document by it, so it cannot be replaced.
  • A request that has a hidden secret and would have the package carry storage/origins.jsonl. That entry holds each value exactly as the area held it, and a page can store what a behavior hands it (see ).

Hidden secrets

A package MUST NOT hold an occurrence of the value of a hidden secret in any of its files: datapackage.json, datapackage-digest.json, the WARC files in archive/ once decompressed, and every other entry. [[BROWSERHIVE-WARC-PROFILE]] says this of a single WARC file and has no way to say it of the rest of the package.

Where this specification has the package record a URL, the producer MUST replace each occurrence in it with the three characters ***, and the result stays a URL, as that specification has WARC-Target-URI stay a URI. Where replacing takes away the scheme of the URL, the producer writes that scheme and a colon in front of the result. Where what is left is still not a URL, as when a value begins inside a port, it writes only the scheme, a colon and ***. That covers:

  • url in document;
  • the URLs in bodylessUrls, truncatedUrls and uninterceptedUrls, and url in crashedTargets (see completeness);
  • url on each line and each node of accessibility/axtree.jsonl;
  • url and the searchable key of each line of the CDXJ index; url is the WARC-Target-URI of the record the line names, and the key is made from it after replacing;
  • url in snapshots and on the entries of pages/pages.jsonl that list a snapshot, which are the WARC-Target-URI of its resource record and have the value of any secret replaced there.

A sorted array of these URLs is sorted as it is written, after replacing. Replacing can make two URLs the same, and an array that lists a URL once then lists that URL once. Nothing marks such a URL as replaced, and a reader cannot tell *** there from the same characters in a URL.

The producer MUST also replace each occurrence with *** in the text and title of an entry of pages/pages.jsonl, in the title of datapackage.json, in the name and value of a node of accessibility/axtree.jsonl, in the msg and data of a line of logs/capture.jsonl (see ), and in the url, the url of initiator and the error of a line of trace/events.jsonl (see ). The url of a line of the trace and the url of its initiator are not among the URLs listed above: the producer replaces in them as it does in text, and what it writes there need not stay a URL, because a URL it cut, the way it writes a data: URL and the replacing of a kept secret do not always keep the form of one.

Outside the WARC files, nothing else in a package is replaced: the source of a behavior or a preload script, behaviors/runtime.js, an entry of variables or urlPolicies, a host in tls, an origin in storage, the other members of a line of trace/events.jsonl, the names of members. A capture that would write an occurrence in any of these MUST NOT produce a package.

[[BROWSERHIVE-WARC-PROFILE]] has the producer treat the value of certain cookies as that of a hidden secret from the moment the response that set the cookie arrives. Such a value has no name in secrets. From that moment the producer MUST replace it wherever this section has it replace an occurrence, and nothing more is asked of it: what the producer had received or written before then may hold it, and so may what it copies from the capture request, such as the first entry of pages/pages.jsonl, and what is not replaced.

Kept secrets

A request keeps a secret so that a reader can see what crossed the wire. The value of a kept secret stays in the request, response and metadata records of the WARC, apart from the records of a snapshot. It stays in the URLs the package records of those exchanges and of the document: url in document and on each line of accessibility/axtree.jsonl, the URLs in completeness, and url and the searchable key of the CDXJ lines of responses. When the URL the capture was asked for holds it, it stays in that URL: in the first entry of pages/pages.jsonl, in mainPageURL, and in the description of a warcinfo record and the title of datapackage.json when the producer writes that URL there. It also stays in what says is not replaced, and in storage/origins.jsonl, which holds each value exactly as the area held it.

A package MUST NOT hold the value of a kept secret as it is, whatever its length, in any of these. The producer replaces it there with ***.

  • A snapshot, and its URL ([[BROWSERHIVE-WARC-PROFILE]]).
  • The text and title of an entry of pages/pages.jsonl, and the title of datapackage.json when it is read from the page.
  • The name, value and url of a node of accessibility/axtree.jsonl.
  • The msg and data of a line of logs/capture.jsonl.
  • The url, the url of initiator and the error of a line of trace/events.jsonl (see ).

A kept value that is, or holds, the value of a hidden secret is replaced as far as that value goes: the rules for the hidden secret come first, in the records of the WARC as well.

Keeping a secret lets a reader see what was sent and what came back. What is read from the page is a different record: it holds what a behavior typed into a field, and it is what people read and search. This has a cost. The url of a node no longer names the record of a resource whose URL holds a kept secret, and a short value also replaces text that has nothing to do with it: with the value pro, the word probe becomes ***be.

The storage member

browserhive:capture MUST contain a member storage recording what web storage the captured origins held. The member records the presence and shape of that storage; it MUST NOT contain stored values.

The prohibition is on this member, not on the package. The values themselves live in a separate entry, storage/origins.jsonl, which a package carries when they were asked for; see . They are kept apart because web storage routinely holds bearer tokens and session identifiers, which appear in no WARC payload: a package that recorded them by default would carry them everywhere it went. valuesRecorded states which of the two a package is holding.

Web storage is recorded because it cannot be reconstructed later. It never crosses the network, so no WARC record holds it: a page that renders from localStorage renders from data the archive does not contain. Without this member a reader cannot tell such a page from one that genuinely had nothing to show, and completeness does not help — it reports bodies the package does not hold, and storage never became a body. 

{
  "browserhive:capture": {
    "storage": {
      "profile": "browserhive:storage/2",
      "stage": "after-behaviors",
      "valuesRecorded": false,
      "origins": [
        {
          "origin": "https://www.example.co.jp",
          "local": { "keys": 2, "bytes": 32, "digest": "sha256:b58f31fdc511fb94c356ae7f6d64ac71e5bf056584653c3f3ec61a1f08bfaa0f" },
          "session": { "keys": 1, "bytes": 13, "digest": "sha256:8ce272dea9fc6d7902b23f10411da49a7fb2e3c954ba9f1580cc087292eaafc2" }
        },
        { "origin": "https://ads.example.net", "unreadable": true }
      ]
    }
  }
}

Members

storage MUST contain profile, stage, valuesRecorded and origins.

  • profile — the rules the member follows. For this version of this specification the value MUST be "browserhive:storage/2". A producer that changes what it records, or how a digest is computed, MUST change this value.
  • stage — the point in the capture at which storage was read. For this version the value MUST be "after-behaviors". The stage is normative because the content changes: a page writes to storage as it runs, so a reading taken before behaviours ran and one taken after describe different states.
  • valuesRecorded — whether this package also carries the stored values, in the directory defined below. It says the values were asked for, not that every origin's are present: an origin marked valuesOversize has none. See .
  • origins — an array with one entry per origin the capture could observe.

Origin entries

Each entry MUST contain origin, the origin in the serialised form of [[WACZ]]'s enclosing document — scheme, host and, when not the default, port.

Web storage is partitioned by origin, and a page routinely embeds documents from origins other than its own — an advertisement, an analytics frame, an embedded player. Each of those has its own storage, which the page's own origin cannot see. So this is not a record of “the page's storage”: it is one entry per origin the capture was able to observe, and an entry for a third party is the expected case rather than an anomaly.

An origin that cannot hold storage at all — an opaque origin, such as a document at about:blank or a data: URL — has nothing to record and does not appear.

An entry MUST contain either both local and session, or the single member unreadable with the value true. The second form says the capture could not read that origin's storage. It is distinct from an origin whose storage was empty, which is written as areas with "keys": 0. Recording them the same way would put back the ambiguity this member exists to remove.

An entry here and a line in storage/origins.jsonl are two halves of one record. The entry says what an origin's storage looked like — how many keys, how many bytes, which digest — and is always present. The line says what it contained, and is present only when the values were asked for; valuesRecorded states which of the two a package holds. Two things leave an origin without a line even then: there was nothing to put in one, recorded as unreadable, or what there was to put in one was too large, recorded as valuesOversize. The entry distinguishes them, which is why it is the half that is always written.

local and session each MUST contain:

  • keys — the number of keys the area held.
  • bytes — the total size of the area, counted as the UTF-8 encoding of every key and value. Not UTF-16 code units, which is what the browser's own quota accounting uses.
  • digest — "sha256:" followed by the lowercase hexadecimal SHA-256 of the area, computed over the keys sorted by code point, each contributing key U+0000 value U+0000 in UTF-8. The sort and the separator are normative: without them the same content yields different digests, and the digest exists to be compared across captures.

A digest MUST NOT be treated as a commitment to the value. The values are frequently low entropy — a flag, a theme name, a timestamp — and such a digest is trivially reversed by guessing.

An entry MAY contain valuesOversize with the value true. It says this origin's stored values were not carried because they were too large, and that the entry is therefore everything the package holds about it. It MUST NOT appear alongside unreadable, since storage that could not be read has no size to have exceeded; and it MUST NOT appear when valuesRecorded is false, where no origin's values were going to be carried and the member would report a decision nobody made.

An entry carrying valuesOversize MUST still carry local and session. This is the difference from unreadable and it is deliberate: the capture did read this origin, so it knows how many keys there were and how large they were. A reader shown those figures beside the member knows both that values are missing and how much is missing, and can decide whether to capture the page again with a larger bound. Writing the entry without its areas would throw away a measurement already in hand. 

{
  "origin": "https://heavy.example",
  "local": { "keys": 1, "bytes": 2129905, "digest": "sha256:1aeb74b512b17f6fc43ade8575d452df142ade5d1515a4afcaf05dd199688c38" },
  "session": { "keys": 0, "bytes": 0, "digest": "sha256:e3b0c44298fc1c149afbf4c8996fb92427ae41e4649b934ca495991b7852b855" },
  "valuesOversize": true
}

The storage directory

[[WACZ]] permits additional files and directories, provided they stay out of archive, indexes and pages, and are listed in the resources section of datapackage.json. A conforming package MAY use that allowance.

A conforming package MAY contain an entry at storage/origins.jsonl. When present, it MUST be declared in resources like any other file, and it MUST be JSON Lines: one JSON object per line, each object recording the web storage one origin held.

When the entry is present, valuesRecorded MUST be true. When it is absent, valuesRecorded MUST be false. A reader can therefore tell whether a package carries stored values without opening the archive body.

A package that has a hidden secret MUST NOT contain the entry, so its valuesRecorded is false (see ). 

{
  "profile": "browserhive:storage/2",
  "origin": "https://www.example.co.jp",
  "takenAt": "2026-09-06T01:22:14.881Z",
  "stage": "after-behaviors",
  "areas": {
    "local": { "feed.cache": "[{\"id\":1}]", "ui.theme": "dark" },
    "session": { "nav.scroll": "820" }
  }
}

Each line MUST contain profile, origin, takenAt as an [[RFC3339]] timestamp, stage and areas. areas MUST contain local and session, each an object mapping key to value exactly as the area held them. An origin recorded as unreadable or valuesOversize in storage MUST NOT have a line here. The entry MAY therefore contain no lines at all, when the values were asked for but no origin's could be carried. That is not the same as the entry being absent, which says they were never asked for.

The accessibility directory

[[WACZ]] permits additional files and directories, provided they stay out of archive, indexes and pages, and are listed in the resources section of datapackage.json. A conforming package MAY use that allowance.

A conforming package MAY contain an entry at accessibility/axtree.jsonl. When present, it MUST be declared in resources like any other file, and it MUST be JSON Lines: one JSON object per line, each object recording one snapshot of the accessibility tree the browser computed for the captured page.

A package whose document carries withheld MUST NOT contain this entry. The tree is read from the rendered page, so it carries the text of the document even when a policy kept that document's body out of the archive.

The tree is recorded because it cannot be reconstructed later. It is derived from the DOM and the layout tree, it contains nodes with no corresponding DOM node (CSS generated content, list markers), and aria-owns reparents nodes so its shape differs from the document tree. Replaying the archive against a future browser produces a different tree. This is the same reason tls is recorded rather than referenced.

Snapshot members

Each line MUST contain the members profile, url, takenAt, stage and tree.

  • profile — the pruning rules the line follows. For this version of this specification the value MUST be "browserhive:axtree/1". A producer that changes the pruning rules MUST change this value, so a reader can tell what was discarded.
  • url — the URL of the document the snapshot was read from. It MUST equal the url of document.
  • takenAt — when the snapshot was taken, as an [[RFC3339]] timestamp.
  • stage — the point in the capture at which the snapshot was taken. For this version the value MUST be "after-behaviors". The stage is normative because the tree changes. Autoscroll triggers lazy loading, so a tree taken before behaviours ran and one taken after describe different pages.
  • tree — an array of nodes, described below.

A line SHOULD also carry devicePixelRatio, viewport and nodes — respectively the pass the snapshot came from, the viewport in effect, and the number of nodes before pruning. The last of these lets a reader see how much was discarded. 

{
  "profile": "browserhive:axtree/1",
  "url": "https://www.iana.org/",
  "takenAt": "2026-08-22T02:55:56.759Z",
  "stage": "after-behaviors",
  "devicePixelRatio": 1,
  "viewport": { "width": 1280, "height": 800 },
  "nodes": 255,
  "tree": [
    {
      "role": "RootWebArea",
      "name": "Internet Assigned Numbers Authority",
      "children": [
        { "role": "heading", "name": "Domain Names", "level": 2 },
        { "role": "image", "name": "logo",
          "url": "https://www.iana.org/_img/iana-logo-header.svg" }
      ]
    }
  ]
}

Shown across several lines for readability. In the file each snapshot occupies exactly one line.

Node shape

Every node MUST carry role. A node MUST NOT carry any member other than role, name, level, url, checked, expanded, disabled, required, value and children.

Two of those carry more weight than the rest:

  • level — the heading depth. Without it a heading node cannot be told from another, and the document structure the tree exists to record is lost.
  • url — the reference an image or link points at. It is what connects a node to the response recorded in archive/, so a reader can go from “there was a chart here” to the bytes of that chart.

A member whose value is absent, empty or false MUST NOT be written. Writing defaults on every node costs more than the content it surrounds.

Pruning

Nodes the browser marks as ignored MUST NOT appear in tree. Their children MUST be kept and attached to the nearest retained ancestor.

This is what keeps hidden text out of the record: subtrees removed by aria-hidden or display: none are ignored nodes, so they never reach the file. A reader can therefore treat the tree as a description of what was visible, which is a stronger claim than anything the WARC payload alone supports.

Nodes whose role is generic, none or InlineTextBox MUST NOT appear in tree either, and their children MUST be kept in the same way. These roles carry no meaning of their own; keeping them doubles the depth of the tree without adding anything a reader can use.

A producer MUST NOT drop nodes for being outside the viewport. Doing so is reasonable for an agent, which can only act on what it can see, but an archive that discards the part of the page nobody scrolled to is not a record of that page.

The behaviors directory

[[WACZ]] permits additional files and directories, provided they stay out of archive, indexes and pages, and are listed in the resources section of datapackage.json. A conforming package MAY use that allowance.

A conforming package MAY contain entries under behaviors, carrying the code the capture ran on the page before archiving it. When present, each entry MUST be declared in resources like any other file.

The code is recorded because it cannot be recovered later. Code the producer ships is at least pinned by build, but code a request carried arrives with the request and is gone once the response is discarded — and the name it ran under was chosen by whoever supplied it, so two runs of different code under one name are otherwise indistinguishable. This is the same reason tls is recorded rather than referenced.

Runtime

A conforming package MAY contain an entry at behaviors/runtime.js. When present, it MUST be the source the producer evaluated in the page, byte for byte.

It MUST be present when the producer evaluated such a source, and MUST NOT be present otherwise. Its presence therefore states that code ran on the page — whether or not any behavior went on to do anything.

After evaluating that source, the producer MAY call a function the source defined, with arguments. The call and its arguments are not part of the source and are not recorded here. Of the arguments, the variables are in settings.variables and the names of the secrets in settings.secrets. The values of the secrets are not recorded as arguments anywhere, and the producer MUST NOT write them into the source; what becomes of them once a behavior has them is set out in .

This is what lets the runtime be the same bytes for every capture a producer makes. A producer that wrote the values into the source would record a different runtime.js for each capture — and would record the secrets with it.

“Byte for byte” is the requirement, not readability. A producer that minifies its runtime records the minified form, because that is what the page received. A reader who wants the form a person can read has build, which names the software that produced the package.

Request-supplied behaviors

A conforming package MAY contain an entry at behaviors/custom.jsonl. When present, it MUST be JSON Lines: one JSON object per line, each object recording one behavior that arrived with the capture request. 

{
  "profile": "browserhive:behaviors/1",
  "id": "example.com:gallery",
  "source": "class { static id = \"example.com:gallery\"; … }"
}

Each line MUST contain profile, id and source.

  • profile — the rules the line follows. For this version of this specification the value MUST be "browserhive:behaviors/1".
  • id — the name the behavior was registered under. Every entry in settings.behaviors whose origin is "custom" MUST have a line here. The converse does not hold: a line MAY have no matching entry, because a behavior can be placed in the page and then decline to act.
  • source — the code as it arrived, byte for byte.

The entry MUST be present when the producer placed any request-supplied behavior in the page, and MUST NOT be present otherwise. Its absence therefore states that the package holds no code that came from the request.

The condition is placement, not execution — the same condition as the runtime. Code that was put into the page ran there, whatever it then decided to do, and an archive that recorded only the code that acted would omit code that executed.

A behavior name is chosen by whoever supplied the behavior, and nothing constrains it — the names in use today contain both : and /. Using them as entry paths would let a name decide where a file lands inside the package. One file, one line per behavior, keeps the name a value rather than a path.

Reading these entries

A reader MUST NOT execute the contents of behaviors. They are a record of what the producer ran, not part of the archived page, and nothing in the package requires them to be run again for it to be replayed.

This is stated because the entries are the only ones in a conforming package whose contents are executable, and because a reader that replays a package has an execution context already open.

The preload directory

A conforming package MAY contain entries under preload, carrying code a request supplied to run before the captured page's own scripts. When present, each entry MUST be declared in resources like any other file.

Code under behaviors runs once, on the main frame, after the page has loaded, and can report what it decided. Code under preload runs before any of the page's own scripts, in every frame including subframes, again on every navigation, and has no way to report anything. A reader asking “what could this code have observed, and how many times” gets a different answer for each, so a package that mixed them into one list would answer neither question.

Supplied scripts

A conforming package that ran preload scripts MUST record them at preload/scripts.jsonl, one JSON object per line, in the order they were registered. Each line MUST carry profile, the string "browserhive:preload/1"; id, the name the script was supplied under; and source, the script exactly as it was evaluated.

The id MUST NOT determine the entry's name inside the package. It is a value on the line.

Names are supplied by whoever sent the script and are not constrained, so a name that looks like a path would otherwise decide where the entry sits. This is the same rule the request-supplied behaviors follow, and for the same reason.

Reading these entries

A reader MUST NOT execute the contents of preload. As with behaviors, they are a record of what the producer ran, not part of the archived page.

Reading this entry

A reader MUST NOT execute the contents of logs/capture.jsonl. The lines are a record of the capture, not part of the archived page. Code that appears in a line is something the page or a behavior wrote down, and nothing in the package asks for it to be run.

A reader MUST NOT take a line whose source is "page" as a statement of the producer. The producer passes on what the captured page wrote, and the page chose the words — including words that read like the producer's.

Nor is a line whose source is "script" proof that a behavior wrote it. A behavior writes its lines through a channel in the page's main world, where the page's own scripts run too, and the producer attributes each line to a behavior by the code it came from, or, when it cannot tell, to the behavior running at the time. A script of the page can therefore write lines that read as a behavior's. Only the lines whose source is "browserhive" are the producer's own account.

A log without lines from the page does not say that the page wrote none. The producer need not listen everywhere a page can write — in every kind of worker, for instance — and the lines it leaves out are counted, not kept.

The trace directory

[[WACZ]] permits additional files and directories, provided they stay out of archive, indexes and pages, and are listed in the resources section of datapackage.json. A conforming package MAY use that allowance.

A conforming package MUST contain an entry at trace/events.jsonl, the trace of its capture: the requests the capture saw begin, and what became of each. It MUST be declared in resources like any other file, and it MUST be JSON Lines: one JSON object per line, each object recording one request.

The entry MUST be present even when the trace has no lines, as an empty file, so that an empty trace is a claim rather than an omission. A package without the entry does not conform to this version. In a package written against an earlier version, which did not define the entry, its absence says nothing about the requests the capture made.

This profile asks nothing of how the entry is stored in the ZIP file. Like the other text entries of a package, it MAY be compressed there: a reader reads it whole, and does not seek into it by offset as it does into a WARC file.

The records that [[BROWSERHIVE-WARC-PROFILE]] defines hold the exchanges the capture kept, and say when each began. They do not say how long an exchange took or what in the page asked for it, and they hold nothing of a request that was still unanswered when the capture stopped. That is what a reader needs when a page in the archive lacks something: whether the request was never made, was made and failed, or was still on its way. Declared in resources, the entry is covered by the package's digests, and by its signature when it has one.

Each line records one request: one the browser began, or one the producer kept it from sending. The producer makes the line when the request begins and fills it in as the response, the end or the failure reaches it, so a request that had not ended when the producer stopped recording is in the trace all the same, as "pending". A response that redirects ends its line, as it ends its exchange in [[BROWSERHIVE-WARC-PROFILE]], and the request that follows begins another line. Lines that share an id MUST be in ascending order of hop, and two of them MUST NOT carry the same hop.

The lines MUST be in the order the producer made them. That is not an order of time: neither startedAt nor ms is required to be at or above that of the line before. The entry MUST hold a line for every request whose start reached the producer, and every request it kept from being sent, before it stopped recording, except the ones it leaves out as described below.

The start of a request reaches the producer in one of two ways. The browser reports a request that begins on the captured page's side, and times it by its own clock. A request the producer kept from being sent enters the trace through the producer's own decision, and is timed by the producer's clock. Those two are the lines BrowserHive makes, and a request it kept from being sent has a line wherever in the page it was made, inside a frame from another site or a worker included. Sorting the lines by a time would claim an order between events that nobody observed in that order. A reader that wants one sorts by ms, and knows what it did.

The producer closes the trace once, after it has stopped recording the network and before it assembles the package. A request the page makes after that is not in it, and a line the producer was still filling in stays as it stood: its outcome is "pending".

record, when present, MUST name a response record in archive/: the one of the exchange the line records. On such a line startedAt MUST be the WARC-Date of that record, character for character. Two lines MUST NOT carry the same record. A line whose exchange has no response record in the package MUST NOT carry record: a line whose outcome is "finished" and that carries none is a response the browser read to its end and the producer wrote no record of — because the capture stopped before the producer had the body, for instance. When dropped in trace is 0, every response record in archive/ MUST be named by the record of a line.

A line reads three clocks, and they are not to be mixed. startedAt is the browser's wall clock, except on a line whose outcome is "denied", where it is the producer's: the browser never began that request. The browser's wall clock is the one WARC-Date is read from, which is what lets a line and a record be laid side by side; but a wall clock can be set while a capture runs, so the difference between the startedAt of two lines is not a length of time. durationMs and timing are differences of the browser's monotonic clock, which does not jump. ms places the line on the axis the log lines are on. A producer need not read its own clock for every line: BrowserHive reads it once, at the first request, and from then on adds what the browser's monotonic clock says has passed.

durationMs runs from the start of the request to its end as the browser reported them, so it includes the time for which the producer held the request or the response to examine it — to match the URL against the policies, or to read the body — and so can the parts of timing. A length here can be longer than the same exchange takes in a browser nobody is recording.

A line whose outcome is "not-archived" or "denied" MUST NOT carry initiator, response, timing, durationMs, encodedBytes or record.

A requester withholds a request so that the package does not keep the exchange. If the line carried the status of the response, its size or how long it took, the trace would be a second place to read what was to be left out, and a policy that held for the WARC would not hold for the package. The line therefore carries no more than the record of a withheld request does — that the page asked for the URL, by which method, for what kind of resource, and what the producer decided — and when. The order of the lines still shows one thing about the response. When the response to a request that a no-archive entry matched is a redirect, and no policy withholds the request that follows, that request has a line of its own with the same id and the next hop. A reader can therefore tell that the withheld request was redirected, and to which URL. The exchange that followed is one the package was to keep, so its records are in the WARC in any case.

A line whose outcome is "failed" MUST carry error, and any other line MUST NOT. endUnobservable MUST NOT be present on a line whose outcome is not "pending". durationMs MUST NOT be present on a line whose outcome is not "finished", "redirected" or "failed", and encodedBytes MUST NOT be present on a line whose outcome is not "finished". Where urlCut, endUnobservable or fromCache is present its value MUST be true.

A producer does not listen everywhere a page can make a request, and the end of a request can be reported where it does not listen: the document of a frame from another site begins on the page's side and ends on the frame's. A "pending" line that carries endUnobservable is such a request. It says that the producer could not have seen the end, not that there was none.

A producer MAY cut url to keep a line within a size of its own. A line whose url it cut MUST carry urlCut. A data: URL holds its content in the URL itself, and that content can be a body the package was not to keep, or text of the page. url and the url of initiator MUST NOT hold the data of a data: URL: the producer writes such a URL no further than the comma that ends its media type, the line MUST carry urlCut when the URL is its url, and what the producer writes in place of the data is its own to choose. BrowserHive writes the length of the URL.

A producer MAY leave lines out to keep the trace within limits of its own. One that does MUST say how many in dropped of trace. Nothing in the entry marks where they were. BrowserHive keeps the lines it made first and the ones it made last, and leaves out lines between them: the last lines are the ones a reader needs when a capture ran out of time.

The producer passes on what the browser said, and the page chose the words.

A trace without a line for a URL does not say that the page never asked for it. Constraints inherited from replay

The requirements in this section do not come from [[WACZ]]. They come from what existing readers of WACZ packages do, and a package that ignores them is unreadable in practice even though it satisfies the base specification.

  • The profile member of datapackage.json MUST be "data-package". Readers switch on this value and reject values they do not know, so it is not available to identify this profile. See .
  • config and metadata in datapackage.json MUST NOT be used to carry values defined by this specification. Readers assign them meaning.
  • Values in the CDXJ index MUST be strings, including those that look numeric.
  • The CDXJ index MUST be stored uncompressed, at a path that does not end in .gz. Readers locate it by extension and do not decompress it.
  • The filename field of a CDXJ line MUST be relative to archive/. Readers prepend the directory themselves, so a line that carries it resolves to archive/archive/… and nothing is found. See .

These are recorded here so a package author can satisfy them. Why each one exists is a matter of implementation history and is documented outside this specification. One more constraint of this kind applies to the WARC records rather than to the package — the form of a response payload — and is stated in [[BROWSERHIVE-WARC-PROFILE]].

Security and privacy considerations

tls is not proof of provenance. Certificates are public: anyone can obtain one and present a copy. Holding these fields says nothing about who answered a request. Two narrower things are worth the storage — issuer changes when a connection is intercepted, and the validity period can be checked against the time the capture claims — and neither survives the capture unless it is written down.

completeness asserts absence, not correctness. It reports bodies this package empirically does not hold. It does not assert that the bodies it does hold are what the origin served. Nor does complete say that no body was dropped for holding the value of a hidden secret: a record of a body not kept whose truncated is secret says that.

What a conforming package does assert about the bodies it holds is the subject of the Payloads section of [[BROWSERHIVE-WARC-PROFILE]]: they are the bytes that crossed the wire, so a payload digest is a digest of what the origin sent, not of a copy the producer re-encoded. The exception is a redacted record whose BrowserHive-Redacted field names payload: values in its body were replaced, and its digest vouches only for the bytes the record holds. Neither says that the origin was the party the URL names; see tls.

A package records URLs in completeness, host names in tls, and in the trace the URL of each request the capture saw begin, including requests a policy withheld and requests that were never answered. Where the captured page carried personal data in URLs, those URLs travel with the archive.

The accessibility tree carries the names the browser computed for elements, which are drawn from the visible text of the page. When the document's body is in the WARC payload, that text is already present there, and the pruning rules make the tree's exposure narrower than the payload's: ignored nodes are excluded, so text hidden by aria-hidden or display: none does not appear in the tree even though it appears in the response body. When a policy kept the document's body out of the archive, that text is not in the payload, and the package carries neither the tree, nor the page's text and title, nor a snapshot read from that document, nor a screenshot, nor the lines the page wrote to the log (see document).

A snapshot carries the page as it stood: its text, and the values in its fields except password fields ([[BROWSERHIVE-WARC-PROFILE]]). Unlike the tree, it is not narrower than the page, and text the page hid is in it. The values of the secrets in settings are replaced in a snapshot, at least as they are and as HTML escapes them, and those of hidden secrets in every spelling an occurrence can take; a secret the page transformed otherwise, or a value nobody declared a secret, stays.

That rule works at the level of the document. The rendered page can hold content that arrived through sub-resources — the response to a script's request, or a frame's document — and a policy that kept one of those bodies out of the archive does not keep its content out of the page-derived records of a document that was kept. A requester who needs that content kept out entirely has to keep the document out. The screenshots are the one exception, and only for some kinds of request (below).

A screenshot carries what the viewport showed: the page's text, its images, a frame of a video that was playing, the documents of its frames, frames from other sites included, and what the page and the behaviors had put into its fields. It is a picture, so nothing in it can be searched for or replaced. That is why a package holds no screenshot at all — rather than one with something taken out — when the capture was given a secret, when it had a media type policy, when a no-archive or no-body entry of urlPolicies matched a request the browser reported as one for a document, an image or media, or when the document is withheld (see screenshots).

Those conditions do not reach everything a picture can show. A value nobody declared a secret is in the picture if the page showed it. So is what the page drew from a response to a request that a no-archive or no-body entry of urlPolicies matched and that the browser reported, wherever the producer read it, as neither a document, an image nor media: text a script fetched and wrote into the page, the look a style sheet gave it, the glyphs of a font. The browser's word for the request decides, and an image that a script fetches and draws by itself is, to the browser, the script's request. The same goes for video and audio that a script fetches in pieces and hands to a player: the browser reports those requests as the script's, so a URL policy that matches them leaves the screenshots in. A media type policy does not, because any such policy takes them out. Nor does the rule reach a request the producer does not see. A requester who needs such content out of the pictures as well has to keep the document out, or have the capture made by a producer that takes no screenshots.

The conditions also reach further than what a picture shows. A page that loads a single image a policy withholds — a tracking image nobody can see, under a policy that withholds an analytics host — has no screenshot in any capture: the producer does not keep the body, so it cannot tell an image that was visible from one that was not. A request that such a policy matched and that only redirected, bringing the page nothing to show, counts as well, because the producer decides at the request. A media type policy takes the screenshots out of every capture made under it, whether or not a response matched it. And a policy that applies to a request made after a picture was taken takes that picture out too, because the producer cannot tell which picture shows which response.

A tool that reads a package can check the marks the package carries: secrets, contentTypePolicies, withheld in document and in snapshots, the records of withheld requests, and the records of bodies not kept beside the lines of the trace. Those marks are not the whole of what binds the producer. A tool cannot see a request the producer wrote no record of, such as one made inside a frame from another site or one no response answered, and it cannot see whether taking a picture changed the page. Nor can anyone holding only the package check that the pixels are what the browser showed: the digests of the package, and its signature when it has one, cover the bytes of the picture and say nothing of how they were made.

The log carries text the page wrote. The lines whose source is "page" hold what the captured page's scripts wrote to the console and the errors they did not catch, which routinely include URLs, identifiers and the page's own text. When the document was withheld, the log holds none of them (see ). That requirement looks only at the document that document names, and a line does not say which document wrote it, so when the page moved on from a withheld document to one that was kept, the first document's lines would stay. A producer may therefore leave out every line of the page whenever snapshots records a stage as "withheld", and one that does says so in a line of its own, so a reader can tell that the page's lines were left out rather than never written.

In the log, the producer replaces the value of a secret wherever it appears as it is — in msg and in data, in a key or a value, at any depth, whatever its length — and that of a hidden secret in every spelling an occurrence can take. A behavior that writes a secret in any other form, hashed or split, puts that form in the package, and a value nobody declared a secret stays. And the channel a behavior writes its lines through is in the page's main world, so the page's scripts can write lines that read as a behavior's (see ).

The trace says which URLs the page asked for, what in the page asked for them and how long each exchange took. Of a request a policy withheld, a line carries what the WARC does — the URL, the method and the kind of resource — and not the status, the size or the timing of a response (see ). One thing about the response can still be read from the order of the lines: when a request that a no-archive entry matched was redirected to a URL no policy withholds, the next line shares its id and carries the next hop, so a reader learns that the withheld request was redirected, and where to. The exchange it was redirected to is in the WARC in any case, because it is one the package was to keep. In its lines the producer replaces the value of a secret, kept or hidden, where it appears in a URL or in the text of a failure; a value in any other form stays, and so does one nobody declared a secret. A data: URL is written without its data. What initiator names is the captured page's account of itself, not the producer's, and only the lines inside the package are covered by its digests and its signature: the same lines shown anywhere else are copies (see ).

storage exposes nothing the package did not already hold. It records key counts, byte counts and digests. It does not record values, and a digest is not a value — though, as noted above, a digest over low-entropy content is not a hiding place either.

A package that also contains storage/origins.jsonl does expose more. Web storage routinely holds bearer tokens, session identifiers and unsent drafts, none of which appear in any WARC payload; this is the one place in this profile where a conforming package can carry material the capture never received over the network. Producers SHOULD leave the directory out by default. A reader can tell the two cases apart without opening the archive body, because valuesRecorded says which one this is.

Replacing the value of a secret keeps it out of the package, not out of the page. A behavior reads it from the runtime in the page's main world, where the page's own scripts can read it too, and a producer cannot hide it there without a separate execution context. A behavior that sends it over the network — in a URL, a header or a body — hands it to the origin, whatever the package then records.

A hidden secret is hidden only where the producer recognizes its value. What the Security section of [[BROWSERHIVE-WARC-PROFILE]] lists stays in the package too: what is made from the value, such as a hash, a ciphertext or a token an origin issues in a body; a spelling that is not an occurrence; and the fact that a value was there, which *** shows wherever it stands. The digest of a storage area is made from what the area held, before anything is replaced, so it can let a reader test guesses of a value a page stored. A requester who needs every trace of a secret kept out of the archive has to supply a behavior that does not send it.

A reader holding only the package cannot check that it holds no occurrence, because the package does not hold the value. A tool that reads the package can check the shape of what the producer says it did, and nothing more. A producer can check, since it holds the values: it can look through every file before it writes the package.

secretArchive is the request's to fill in, and it decides what travels. The value of a kept secret stays readable in the records of the WARC and in the URLs taken from them, and whoever passes the package on passes it on.

variables, by contrast, are recorded as values on purpose, and a requester who puts personal data in one has put it in the archive. The line between the two is the request's to draw: this profile records what it was told was a secret and what it was not.

browser names the build that did the recording, and it is required. A producer that presents a different identity to the origin — a substituted User-Agent, for example — does not thereby change this member: what is sent to the server and what the package reports are separate. Operators who treat their build version as sensitive should know that a conforming package discloses it.
